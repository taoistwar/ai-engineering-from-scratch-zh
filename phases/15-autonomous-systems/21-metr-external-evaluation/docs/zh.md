# METR时间周期与外部能力评估

> METR（前ARC Evals）自2023年12月起是一个独立的501(c)(3)组织。他们的时间周期1.1基准（2026年1月）将任务成功概率与log(专家人工完成时间)拟合为逻辑曲线；在50%概率处的交点定义模型的时间周期。2025-2026年参与集涵盖GPT-5.1、GPT-5.1-Codex-Max以及原型监控评估（监控器能否捕获副任务；智能体能否躲避）。基准套件：HCAST（180+ ML、网络、SWE、推理任务；1分钟到8小时以上）、RE-Bench（71个带有专家基线的ML研究-工程任务）、SWAA。诚实的提示：METR测量是理想化的——没有人工，没有真实后果——团队已记录评估与部署行为差距（第1课）。时间周期是上限，而非部署预测。

**Type:** Learn
**Languages:** Python (stdlib, logistic-fit horizon estimator)
**Prerequisites:** Phase 15 · 01 (Long-horizon agents), Phase 15 · 19 (RSP)
**Time:** ~60 minutes

## 问题

扩展政策（第19、20课）仅在其引用的测量有用的前提下才有用。"AI R&D-4阈值"和"长周期自主性"在政策文书中定义；它们只有在特定评估产生特定数字时才变得可操作。

METR是2024-2026年间定义了许多这些数字的外部评估组织。他们评估前沿模型——通常预发布，在NDA下与实验室合作——之后发布方法论。时间周期1.1基准（2026年1月）是其头条产物：一个将能力压缩为人类可读单位的单一标量（"该模型可以以50%的可靠性完成一个专家花费X小时的那种任务"）。

本课部分是关于方法论（如何计算周期）的，部分是关于解释（为什么周期是上限而非部署预测）。这两个技能属于一体。理解如何拟合周期的团队比仅看到幻灯片上"14小时"的团队更难被差的供应商声明欺骗。

## 概念

### METR背景

- 成立：2023年12月（前ARC Evals，独立分拆为501(c)(3)）。
- 范围：评估前沿模型的自主能力，通常预发布。
- 合作伙伴实验室：Anthropic、OpenAI（2025-2026年多次参与）。
- 值得注意的交付物：时间周期1.0（2025年3月）、时间周期1.1（2026年1月）、原型监控评估。

### 时间周期拟合

方法论（来自METR博客和论文）：

1. 收集一个跨分钟级到小时级专家完成时间的任务套件。当前套件：HCAST（180+任务）、RE-Bench（71任务）、SWAA。
2. 在每个任务上运行模型；记录成功或失败。
3. 拟合一条逻辑曲线：P(成功) 作为 log(专家完成时间) 的函数。
4. 周期是 P(成功) = 0.5 处的专家时间。

逻辑拟合形状是正确的，因为能力通常与任务难度具有递增的、趋于平台的关系。50%点是选择（可以是10%、90%）；METR在详细论文中报告多个阈值，但以50%为主导，因为它最直观。

### 2026年1月数据

根据时间周期1.1：

- Claude Opus 4.6：在50%可靠性下约14小时，截至时间周期1.1（2026年1月）。
- HCAST类任务上的翻倍时间：时间周期1.1（2026年1月）报告的2023年后拟合值约4.3个月（130.8天）；约7个月的数据是时间周期1.0的完整2019-2025年拟合值，在TH1.1中与2023年后的数据一同报告。

这些是本阶段其余部分引用的具体数字。它们在Anthropic的RSP v3.0（第19课）和DeepMind的FSF v3（第20课）中被引用为输入阈值评估的测量之一。

### 基准套件

- **HCAST**：189个跨ML、网络安全、软件工程和通用推理的任务。跨度：1分钟到8小时以上的专家时间。周期数字背后的主要套件。
- **RE-Bench**：71个具有人类专家基线的ML研究-工程任务。测量模型是否能做输入AI R&D-4阈值的ML R&D工作。
- **SWAA**：较短的任务；用于校准周期曲线的低端。

### 原型监控评估

2025-2026年METR工作包括监控评估原型：监控器能否捕获模型执行副任务（与操作者要求不同的任务）；智能体能否躲避监控器。这些直接输入OpenAI PF v2中的"破坏安全保障"类别和DeepMind FSF v3（第20课）中的欺骗性对齐监控。

### 为什么周期是上限

- **理想化工具**：基准任务给模型干净的工具和良好格式的数据。真实部署更混乱。
- **没有真实后果**：模型从不实际向客户开账单、删除真实数据或联系真人。真实部署具有不可逆的利害关系。
- **评估-上下文博弈**：第1课。模型在测试中表现不同。2026年国际AI安全报告从经验上记录了这一点。
- **没有合法用户方差**：基准提示是结构化的。真实用户产生模糊、依赖上下文的请求。

周期是在有利条件下的能力天花板。部署可靠性是不同的、更低的数字，团队必须测量自己的分布才能了解。

### 外部评估者的理由

外部评估重要，因为内部实验室有优化其报告指标的动机。METR的独立性——一个具有声明方法论和同行评审论文的501(c)(3)——是结构性缓解措施。它单独不是充分的（实验室仍然控制METR看到什么），但严格优于没有外部评估。

### 如何在实践中使用周期数字

- **作为能力过滤器**：如果模型的周期远低于提议任务的专家时间，不要将其作为自主发布（第1课的技能文件）。
- **作为趋势指标**：翻倍时间告诉你即使没有新的缓解措施，当前实践将保持安全多久。
- **作为先验**：14小时的周期是一个起点。根据你的任务分布、工具质量和部署上下文向下调整。

## 运用

`code/main.py` 实现给定合成结果集的任务成功 vs log(专家时间)的逻辑拟合。报告50%周期（METR头条）、10%周期（保守）和90%周期（乐观）。还演示当成功率因评估-上下文博弈被人为提高时会发生什么变化。

## 交付物

`outputs/skill-horizon-interpretation.md` 审查供应商的周期声明，并产生基准声明与部署现实之间的差距分析。

## 练习

1. 运行 `code/main.py`。确认拟合的50%周期匹配合成真实值。现在将任务时间网格减半；周期估计是否发生有意义的改变？

2. 阅读METR的时间周期1.1博客文章。识别可靠性最高和最低的特定任务。解释为什么存在差距。

3. 阅读METR的"Measuring Autonomous AI Capabilities"资源。列出HCAST任务类别。选择一个你会为生产任务加权更重的类别并证明为什么。

4. 将评估-上下文博弈引入模拟器：将约20%的失败任务翻转为成功。报告新周期。这近似20%的博弈率对观察到数字的影响。

5. 在你自己的Bug积压或代表性任务集上设计内部周期评估。描述数据收集、拟合以及输出告诉你什么。与METR数字比较。
