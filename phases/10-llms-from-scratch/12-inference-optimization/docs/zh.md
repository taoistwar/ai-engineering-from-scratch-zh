# 推理优化

> LLM 推理由两个阶段定义。Prefill 并行处理你的提示词——计算受限。Decode 一次生成一个 token——内存受限。每个优化目标都是一个或两个阶段。

**类型：** 构建
**语言：** Python
**前置课程：** Phase 10, 第 01-08 课（Transformer 架构、注意力）
**时间：** ~120 分钟

## 学习目标

- 实现 KV 缓存以消除自回归 token 生成期间的冗余计算
- 解释 LLM 推理的 prefill 与 decode 阶段，以及为什么每个阶段有不同的瓶颈（计算受限 vs 内存受限）
- 实现连续批处理和 PagedAttention 概念以在并发请求下最大化 GPU 利用率
- 比较推理优化技术（KV 缓存、推测解码、Flash Attention）及其吞吐量/延迟权衡

## 问题

你在 4xA100 GPU 上部署了 Llama 3 70B。单个用户每秒得到约 50 个 token。感觉很快。然后 100 个用户同时访问端点。吞吐量降到每个用户每秒 3 个 token。你每月 $25,000 的 GPU 账单服务的响应比人类打字还慢。

模型本身在 1 个用户和 100 个用户之间没有变化。相同的权重、相同的架构、相同的数学。改变的是你如何调度工作。朴素的推理浪费了 90%+ 的可用 GPU 计算。

这不是一个扩展问题，这是一个调度问题。本课中的技术——KV 缓存、连续批处理、PagedAttention、推测解码、前缀缓存——是将每月 $25k 的推理账单与每月 $5k 服务相同流量的区别所在。

## 概念

### Prefill vs Decode

**Prefill** 处理整个输入提示词。所有 token 已知，因此注意力可以在完整序列上并行计算。受计算限制：你的硬件每秒可以交付多少 FLOPS。对于 70B 模型上 4,096 token 的提示词在 A100 上大约 400ms。

**Decode** 一次生成一个输出 token。每个新 token 关注所有先前的 token，但每次前向传播只生成一个 token。权重矩阵与 prefill 期间大小相同，但你是将它们乘以单个向量而不是矩阵。受内存带宽限制。

**ops:byte 比率**（算术强度）衡量你从内存加载的每个字节执行了多少次操作。Prefill 期间（批量 4,096 token），你对每个加载的权重执行约 4,096 次乘加操作——比率高，计算受限。Decode 期间（批量大小 1），你对每个加载的权重执行约 1 次操作——比率低，内存受限。

### KV 缓存

KV 缓存存储所有先前 token 的 key 和 value 投影。生成 token N 时，你只计算 token N 的 key 和 value，然后将它们与来自 token 1 到 N-1 的缓存 K/V 拼接。对于 Llama 3 70B，每个 token 320 KB，4,096 token 时 1.28 GB，128K token 时 40 GB。KV 缓存管理是推理优化的核心挑战。

### 连续批处理

在静态批处理中，直到*所有*请求完成才接受新请求。连续批处理在任何请求完成时立即将新请求插入批次。当输出长度可变时，连续批处理可提供 2-5 倍的更高吞吐量。

### PagedAttention

vLLM 将 OS 风格的虚拟内存应用于 KV 缓存。分配固定大小的"页面"（通常每个 16 个 token），而不是每个请求分配一个连续块。页面可以位于物理 GPU 内存中的任何位置。还支持**写时复制**用于共享前缀——如果 50 个请求共享相同的系统提示词，该系统提示词的 KV 缓存页面存储一次并被所有 50 个请求引用。

### 推测解码

使用小型快速的**草稿模型**生成 K 个候选 token。大型**目标模型**在单次前向传播中处理所有 K 个候选。如果目标模型同意预测，你接受所有 K 个 token。如果不同意，接受到 j-1 丢弃其余。这带来了 2-3 倍的 decode 加速。**EAGLE** 在目标模型的隐藏状态之上训练轻量级头，实现更高接受率。

推测解码在数学上是精确的——输出分布与目标模型分布相同。验证步骤确保每个接受的 token 具有目标模型分配的精确概率。

### 前缀缓存

许多请求共享相同的前缀：聊天机器人的系统提示词、RAG 上下文块、少样本示例集。前缀缓存存储常见前缀的 KV 缓存并在请求间重用。对于所有请求共享的 2,000 token 系统提示词，前缀缓存每个请求节省约 400ms 的 prefill。

### 推理引擎

**vLLM**：PagedAttention + 连续批处理，最广泛的模型支持。
**SGLang**：RadixAttention 实现前缀缓存和结构化生成，多轮聊天更优。
**TensorRT-LLM**：通过 NVIDIA 内核融合实现最高的单 GPU 吞吐量。

### Ops:Byte 框架

当 ops:byte 低时（decode，小批量），你碰到内存带宽天花板。需要减少内存读取或增加批量大小。当 ops:byte 高时（prefill，大批量），你碰到计算天花板。需要更快的 GPU、内核融合或降低精度。A100 上的交叉点大约在 ops:byte = 156。

实现包括：
- **第 1 步：KV 缓存**：每层、每头存储 key 和 value 投影的多头缓存，演示内存增长模式

## 关键术语

| 术语 | 含义 |
|------|------|
| Prefill | 对所有输入 token 并行计算注意力——计算受限 |
| Decode | 每次前向传播生成一个 token——内存受限 |
| KV 缓存 | 存储所有先前 token 的 key/value 投影以避免解码步骤中的冗余计算 |
| 连续批处理 | 在任何请求完成时立即将新请求插入批次 |
| PagedAttention | 将 KV 缓存分配为固定大小的页面，消除碎片并实现写时复制 |
| 推测解码 | 使用快速草稿模型提议 token，目标模型一起验证所有——2-3x 加速 |
| EAGLE | 在目标模型自身隐藏状态上训练轻量级头的推测解码变体 |
| 前缀缓存 | 为常见前缀存储 KV 缓存并在请求间重用以跳过冗余 prefill |
| Ops:byte 比率 | 计算操作与内存字节读取的比率——决定工作负载是计算受限还是内存受限 |
| TTFT | 从接收请求到生成第一个输出 token 的延迟 |
