# 生产扩展——队列、检查点、持久性

> 将多智能体系统扩展到数千并发运行需要**持久执行**。LangGraph的运行时在每个超级步骤后按`thread_id`写入检查点（默认Postgres）；worker崩溃释放租约，另一worker恢复。智能体可以无限期休眠等待人工输入。**MegaAgent**（arXiv:2408.09955）运行每个智能体生产者-消费者队列，具有三种状态（空闲/处理/响应）和两层协调（组内聊天+组间管理聊天）。**Fiber/async**在LLM流中击败每作业线程：线程99%时间空等令牌，纤程在I/O上合作让步。反论点：Ashpreet Bedi的"Scaling Agentic Software"主张**FastAPI + Postgres + 别无其他**直到负载证明不然——简单架构比预期走得更远。本课构建持久检查点日志，带状态转换的每个智能体工作队列，async-vs-thread演示，并落实务实的"从简单开始"规则。

**Type:** Learn + Build
**Languages:** Python (stdlib, `asyncio`, `sqlite3`)
**Prerequisites:** Phase 16 · 09 (Parallel Swarm Networks), Phase 16 · 13 (Shared Memory)
**Time:** ~75 minutes

## 问题

原型多智能体系统在一台笔记本电脑上用三个智能体在内存事件循环中工作。你移到生产：

- 智能体有时运行数小时（长研究、人在回路中等候）。
- Worker进程崩溃。重启丢失状态。
- 峰值负载是平均值的10倍；你需要水平扩展。
- 用户按智能体运行付费；你需要精确一次语义用于计费。

内存事件循环不做这些。你需要在下面有一套持久执行层。2026年规范选项是：

1. 带检查点的工作流引擎（Temporal、LangGraph运行时）。
2. 带状态存储的消息队列（Postgres + SQS/RabbitMQ）。
3. Actor模型框架（MegaAgent的每个智能体生产者-消费者）。
4. 手工FastAPI + Postgres（Bedi的论点）。

本课构建每种的一个微型版本。

## 概念

### 持久执行，模式

持久执行引擎在每次"步骤"（LangGraph语言中的超级步骤）后持久化完整程序状态。崩溃时：

```
worker中途崩溃
  -> 租约超时
  -> 另一个worker接管thread_id
  -> 从最后检查点恢复
  -> 无重复副作用
```

使其工作的要求：

- **可序列化状态。** 所有智能体状态必须是可持久化的。带活跃数据库连接的函数闭包无法存活。
- **确定性恢复。** 给定相同状态和相同输入，智能体产生相同行动（或对LLM调用推迟到外部确定性预言机）。
- **幂等副作用。** 外部调用（工具调用、支付）必须是幂等的或使用去重键。

LangGraph在每个超级步骤后写入检查点；Temporal在每个活动后写入；Restate使用事件源日志。三者实现相同模式。

### LangGraph的运行时

每个智能体有`thread_id`；状态是类型化字典；每个超级步骤向检查点表写入一行。恢复时，运行时从最后检查点重放，非从头开始。智能体可以`interrupt()`等待人工输入；运行时持久化并释放worker。当输入到达时，任何worker都可恢复。

这是2026年4月的参考生产设计。

### MegaAgent的每个智能体队列

arXiv:2408.09955描述扩展实验：一个集群中数千并发智能体。架构：

```
智能体i：
  状态 ∈ {Idle, Processing, Response}
  入队列   <- 发给智能体i的消息
  出队列  -> 回复 + 副作用

协调器：
  组内聊天  （同一组内的智能体）
  组间管理聊天  （高层路由）
```

两层协调让组内对话密集进行，而组间保持稀疏——用于在数千智能体下保持成本线性的模式。

### Async vs 每作业线程

LLM调用是I/O绑定的。等待下一个令牌的线程99%时间空闲。线程每个约1MB RAM；在10,000并发调用下，仅栈就10GB。

纤程（Python `asyncio`、Go goroutines、Rust `tokio`）在I/O上合作让步。相同的10,000次调用舒适地适合进程。在LLM智能体规模上，async不是优化——它是架构。

异常：CPU绑定后处理（嵌入、分词器技巧）仍想要线程或进程。将你的I/O层与CPU层分离。

### Bedi的反论点

"Scaling Agentic Software"（Ashpreet Bedi，2026年）论证大多数团队在测量负载之前就过度工程化了。务实默认：

- FastAPI + Postgres。
- 每个智能体运行是一行；状态以乐观并发就地更新。
- 通过`pg_notify`或简单Celery worker的后台作业。
- 应用代码中的重试策略。

对于可管理任务上约100以下并发智能体运行，这通常就是你所需要的一切。当你测量到它失败时升级。

规则：当你遇到简单架构无法解决的具体问题时，采用持久执行框架。过早采用烧毁在不会回本的仪式上的时间。

### 精确一次语义

对于付费智能体运行，你需要"有效一次"（至少一次传递+幂等消费者）。工程动作：

- **每次运行的去重键。** 在每个副作用调用中包含它。
- **发件箱模式。** 副作用先写入表，然后独立进程执行它们。两个步骤幂等。
- **补偿事务。** 当副作用成功但其追踪写入失败时，安排补偿。

这些是数据库工程模式，非LLM特定。LLM税只是LLM调用慢；其他一切都是标准分布式系统。

### 彩虹部署

Anthropic的多智能体研究系统使用"彩虹部署"：多个版本智能体运行时并发运行，使长时间运行的智能体不必在每次代码部署时被杀死。在新版流量切片上金丝雀发布；当旧版智能体完成时退役旧版本。

这对长时间运行有状态系统是标准；2026年的适应是智能体可存活数小时，因此部署周期必须适应。

### 规范生产检查清单

- 持久状态（检查点、快照或发件箱+可重放日志）。
- 幂等副作用。
- 用于LLM调用的异步I/O层。
- 带去重的至少一次传递。
- 用于有状态工作负载的彩虹/金丝雀部署。
- 可观测性：每个智能体追踪、超级步骤审计、重试计数器。

## 构建它

`code/main.py` 实现：

- `CheckpointStore`——带线程ID键的SQLite支持检查点日志。每个超级步骤追加一行。
- `run_with_checkpoint(agent, thread_id)`——模拟运行中途崩溃；第二个worker从最后检查点恢复。
- `AgentQueue`——带小工作队列的每个智能体空闲/处理/响应状态机。
- `demo_async_vs_threads()`——通过asyncio和线程运行500个并发模拟"LLM调用"；报告墙钟和峰值内存（近似）。

运行：

```
python3 code/main.py
```

预期输出：检查点恢复在模拟崩溃后成功；async版本在<1s内处理500个并发调用；线程版本花费数秒并使用数量级更多的每并发单元内存。

## 交付物

规范生产加固：

- **从简单开始（Bedi规则）。** FastAPI + Postgres直到你测量到它失败。
- **在优化前对所有测量。** 每次运行延迟直方图、每步时间、重试计数、失败分类。
- **副作用的发件箱模式。** 特别是支付和外部API调用。
- **彩虹部署。** 部署期间永不杀死进行中的智能体运行。
- **在遇到特定问题时采用持久执行引擎（Temporal / LangGraph / Restate）：** 小时级人在回路中等候、跨区域协调、复杂重试/补偿策略。
- **对I/O层使用Async。** 线程仅用于CPU绑定后处理。

## 练习

1. 运行 `code/main.py`。确认检查点恢复有效；测量async vs线程并发差异。
2. 实现**发件箱**表：每个工具调用先写入发件箱，然后独立goroutine/task执行。通过运行工具调用两次验证幂等性。
3. 模拟**彩虹部署**：两个并发运行时版本；将一半新thread_ids路由到每个；确认旧版本上的进行中线程不被中断。
4. 阅读LangGraph运行文文档（见下方链接）。识别运行时中哪些功能在手写FastAPI + Postgres版本中复制最耗时。这是采用的理由，还是你可以推迟？
5. 阅读MegaAgent（arXiv:2408.09955）第3节。两层协调（组内+组间管理聊天）是显式的。勾勒你如何将其映射到具有两个队列族��消息队列。
