# 层次化架构及其失败模式

> 层次化是监督者嵌套。管理者智能体位于子管理者之上，子管理者位于工作者之上。CrewAI `Process.hierarchical` 是教科书版本：一个 `manager_llm` 动态委派任务并验证输出。LangGraph的等价物是 `create_supervisor(create_supervisor(...))`。当任务是真实的组织结构图时，这是自然的模式。它也是最容易崩溃为管理循环的模式——管理者智能体错误分配工作、误读子输出或无法达成共识。顺序模式常常胜过它。

**Type:** Learn + Build
**Languages:** Python (stdlib)
**Prerequisites:** Phase 16 · 05 (Supervisor Pattern)
**Time:** ~60 minutes

## 问题

一旦监督者模式被理解，自然的下一步是"如果工作者本身是监督者会怎样？"团队有子团队；公司有部门的部门。层次化架构映射这一点。

问题是：LLM管理者与人类管理者不同。一个人类管理者对其下属知道什么有稳定的先验判断。一个LLM管理者每回合从其上下文中的任何东西重新推理组织。上下文中微小的漂移，整个树就错误分配工作。

## 概念

### 形状

```
                 管理者
                 ┌─────┐
                 └──┬──┘
           ┌────────┴────────┐
           ▼                 ▼
       子管理A             子管理B
       ┌─────┐           ┌─────┐
       └──┬──┘           └──┬──┘
         ┌┴──┬──┐          ┌┴──┐
         ▼   ▼  ▼          ▼   ▼
       W1  W2  W3         W4  W5
```

每个内部节点规划、委派和综合。只有叶子做工作。

### 它在何处闪耀

- **清晰的组织映射。** 如果真实任务是部门性的（"法务审查文档，财务审查文档，工程审查文档，然后向高管总结"），层次结构是显式的。
- **局部摘要。** 每个子管理者在顶层管理者看到之前综合其团队输出。顶层管理者看到三个子管理者摘要，而非十五个工作者的输出。

### 它在何处出问题

2026年的事后分析一直在发现三种失败模式：

1. **任务分配错误。** 管理者读取目标，幻觉出一个分解，并委派给错误的子管理者。因为子管理者顺从地处理被分配给它的内容，错误只在顶层综合时才浮现——与人类能够捕获该错误的位置相差一个层级。
2. **输出误读。** 子管理者返回"无法验证声明X。"顶层管理者总结为"声明X未被确认。"含义在每个层级漂移。
3. **共识循环。** 两个子管理者不一致；顶层管理者要求它们调和；它们重新向下委派；工作者重新运行；子管理者返回略有不同的答案；循环。CrewAI的 `Process.hierarchical` 用步数限制防止这一点，但限制本身现在是一个超参数。

### 决定性问��

顺序（线性流水线）vs 层次化：你的任务是真有独立子团队，还是模仿树的一条线性流？如果是后者，用顺序。如果是前者，用层次化但预算显式调和规则。

### CrewAI的实现

`Process.hierarchical` 在一个管理者LLM之上连接专家剧组。管理者：

- 接收顶层任务，
- 将子任务分配给剧组，
- 评估剧组输出，
- 决定是接受、重新委派还是迭代。

文档：https://docs.crewai.com/en/introduction（在核心概念下寻找"分层过程"）。

### LangGraph的实现

LangGraph使用嵌套的 `create_supervisor` 调用。内部监督者有自己的图；外部监督者将内部图视为不透明节点。这在调试方面比CrewAI更清晰（你可以分别逐步执行每个图），但更难表达树的动态重塑。

参考：https://reference.langchain.com/python/langgraph-supervisor。

## 构建它

`code/main.py` 运行一个3级层次结构：

- 顶层管理者：将任务拆分为"工程"和"法务"分支，
- 工程子管理者：拆分为"前端"和"后端"工作者，
- 法务子管理者：一个工作者。

演示将愉快路径（每个人都同意）与一个**扰动路径**对比，在其中顶层管理者的分解将"法务"错误标记为"财务"，并观察级联错误——子管理者顺从地做财务工作，顶层综合者报告财务发现，原始法务问题未被回答。

运行：

```
python3 code/main.py
```

输出以清晰的并排对比显示两条路径："被问了什么" vs "交付了什么"。

## 运用

`outputs/skill-hierarchy-fitness.md` 评估给定任务应使用层次化、顺序还是扁平监督者。输入：任务描述、组织结构、调和预算。输出：模式建议及需要防范的特定失败模式。

## 交付物

如果你交付层次化：

- **限制树深度为2。** 三层已经隐藏了大多数错误使其不可观测。
- **显式调和预算。** 在顶层管理者必须提交之前设置最大轮数。通常为2。
- **每个综合上的来源。** 每个节点的摘要必须引用产生它的叶子输出。
- **分解漂移警报。** 记录管理者每步的分解；与用户查询进行对比。如果分解不再覆盖查询，触发警报。

## 练习

1. 运行 `code/main.py` 并比较愉快路径与扰动路径。多少层管理者交接之后顶层输出才与用户问题完全背离？
2. 添加第三层（顶层 → 子 → 子子 → 工作者）。测量扰动路径在深度增长时自我纠正与完全背离的频率。
3. 在每个子管理者处实现一个"金丝雀"工作者，总是被询问原始用户问题不变。使用金丝雀答案检测分解漂移。当金丝雀与综合答案不一致时，管理者应如何反应？
4. 阅读CrewAI的 `Process.hierarchical` 文档。识别CrewAI应用的一个具体护栏（步数限制、manager_llm约束）并描述它针对什么失败模式。
5. 比较嵌套LangGraph监督者与CrewAI层次化。哪个使调和循环更便宜检测？

## 关键术语

| 术语 | 人们常说的 | 实际含义 |
|------|----------------|------------------------|
| 层次化 | "组织结构图模式" | 监督者之上的监督者；只有叶子做工作。 |
| 管理者LLM | "老板" | 在内部节点处分解、分配和验证的LLM。 |
| 分解漂移 | "老板迷失了方向" | 顶层管理者的拆分不再覆盖原始问题。 |
| 调和循环 | "无尽会议" | 子管理者不一致；顶层重新委派；工作者重新运行；循环直到预算耗尽。 |
| 深度2限制 | "不要超过2层深度" | 经验护栏：3层以上会崩塌可观测性。 |
| 金丝雀问题 | "每层的真相基准" | 一个总是被用原始查询不变询问的工作者，用于检测漂移。 |
| 来源链 | "谁说了什么" | 从每个综合追溯到产生它的叶子输出。 |
