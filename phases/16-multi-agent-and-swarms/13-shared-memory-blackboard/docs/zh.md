# 共享内存与黑板模式

> 2026年多智能体系统中两种方法共存：**消息池**（每个人都看到每个人的消息，如AutoGen GroupChat或MetaGPT）和**带订阅的黑板**（智能体订阅相关事件，如Context-Aware MCP或Matrix框架）。两者都是多智能体系统中唯一有状态的部分——这意味着两者都是有趣Bug所在的地方。参考失败模式是**内存污染**：一个智能体幻觉出一个"事实"，其他智能体将其视为已验证，准确率以一种比即时崩溃更难调试的方式逐渐衰减。本课从标准库构建两种结构，注入污染攻击，并展示三种在生产中实际有效的缓解措施。

**Type:** Learn + Build
**Languages:** Python (stdlib, `threading`)
**Prerequisites:** Phase 16 · 04 (Primitive Model), Phase 16 · 09 (Parallel Swarm Networks)
**Time:** ~75 minutes

## 问题

多智能体系统需要一个地方让智能体共享事实。一个字面选项是"通过消息传递一切"——但这用额外复制重新发明了共享状态。另一个是"给每个人一个全局日志"——但全局日志无界增长且容易污染。第三种是"为每个智能体投影视图"——可扩展但模式繁重。

当其中一个智能体幻觉并将幻觉写入共享状态时，读取该状态的每个下游智能体都将幻觉采纳为事实。到人类注意到时，推理链已深至五步，根本原因是第三条写入的消息。调试多智能体准确率衰减比调试崩溃更难。

这就是内存污染。它是MAST分类法（Cemri等人，arXiv:2503.13657）中第二多记录的失败族，并且是结构性的：任何没有来源和不可写入验证者的共享内存设计最终都会表现出它。

## 概念

### 两种主要拓扑

**全消息池。** 每个智能体阅读每条消息。AutoGen GroupChat和MetaGPT使用此方法。简单、透明、可检查，但不能扩展到约10个智能体以上，因为每个智能体的上下文被其他智能体的工作填满。

```
智能体A ──写入──▶ ┌────────────────┐ ◀──读取── 智能体D
                   │   消息池        │
智能体B ──写入──▶ │                │ ◀──读取── 智能体E
                   │ （全局日志）     │
智能体C ──写入──▶ └────────────────┘ ◀──读取── 智能体F
```

**带订阅的黑板。** 智能体声明对主题的兴趣；底层仅路由相关消息。CA-MCP（arXiv:2601.11595）和Matrix去中心化框架（arXiv:2511.21686）使用此方法。扩展更远，但需要前期模式设计使订阅有意义。

```
                   ┌─ 主题: prices ──┐
智能体A ──发布──▶ │                  │ ──▶ 智能体D（已订阅）
                   ├─ 主题: orders ──┤
智能体B ──发布──▶ │                  │ ──▶ 智能体E（已订阅）
                   ├─ 主题: alerts ──┤
智能体C ──发布──▶ │                  │ ──▶ 智能体F（已订阅）
                   └──────────────────┘
```

### 每种何时获胜

- **全池**当智能体少（< 10）、异构且对话是短周期时获胜。当每个人看到一切时，推理谁说了什么很简单。
- **黑板**当智能体多、角色同质但实例众多（群体）且对话长时间运行时获胜。路由节省token成本和上下文污染。

生产系统经常混合：顶层小型全池（规划层），底层黑板（工作者层）。

### 内存污染，一个场景

三个智能体工作在一个研究任务上。智能体A是检索智能体。智能体B是摘要者。智能体C是分析师。

1. A获取一个页面并向共享状态写入一条消息："研究报告42%的准确率提升。"
2. 获取的页面实际说"4.2%的提升。"A幻觉了一个小数点。
3. B，阅读共享状态，写道："大42%准确率增益报告（来源：A）。"
4. C，阅读共享状态，写道："建议采用——42%提升是变革性的。"
5. 最终报告引用了从未存在的42%数字。

没有智能体崩溃。没有测试失败。系统"工作了。"幻觉通过共享状态从一个智能体的上下文越界进入每个下游智能体的推理。

### 为什么这是结构性的

没有共享状态，智能体A的幻觉留在A的上下文中。下游智能体会重新获取或重新推导，可能捕获错误。有天真的共享状态，A的上下文成为每个人的上下文，幻觉被洗白为事实。

问题不是共享状态本身——而是**没有来源和独立验证者**的共享状态。三种缓解措施解决此问题：

1. **为每次写入附加来源。** 共享状态中的每个条目记录谁写的、何时、在什么提示下，以及（如适用）智能体引用了什么来源。下游智能体以与来源相关的怀疑阅读。
2. **版本化写入；将其视为仅追加。** 更正是一个替代旧条目的新条目，而不是就地更新。审计追踪被保留。
3. **保留至少一个不能写入共享状态的智能体。** 一个只读验证者智能体采样条目、重新获取来源，并标记不一致。因为它不能写入池，它不能被池污染。

### 黑板先例（Hayes-Roth, 1985）

黑板模式早于LLM智能体四十年。Hayes-Roth（1985年，"A Blackboard Architecture for Control"）描述了专业的知识源，它们观察全局黑板，贡献部分解决方案，并触发其他源。2026年的黑板（CA-MCP、Matrix）是相同的模式，以LLM智能体作为知识源，以JSON块作为部分解决方案。旧文献已记录写入竞争、机会主义控制和一致性的解决方案，现代系统正在重新发现。

### 投影 vs 全视图

纯黑板给每个订阅者相同的投影（主题限定范围）。一个更激进的设计是**每个智能体投影**：每个智能体获得针对其角色定制的视图。LangGraph的状态reducer是权威的2026年实现——reducer函数将全局状态折叠为角色特定的切片。

每个智能体投影扩展更远，但需要模式。没有模式，你在每个智能体的提示中重新构建临时投影。

### 写入竞争模式

多个智能体同时写入是一个并发问题，而不仅仅是LLM问题。三种模式有效：

- **顺序写入者（单一生产者）。** 所有写入通过一个序列化的协调智能体。简单，但是瓶颈。
- **带版本化的乐观并发。** 每个条目有版本；写入者在版本不匹配时失败并重试。经典数据库技术。
- **主题分区。** 不同智能体拥有不同主题。没有跨主题竞争。需要设计的分区边界。

大多数2026年框架默认顺序写入者，因为LLM调用足够慢，竞争罕见且瓶颈不造成伤害。

### 不可写入的验证者

最具承重性的缓解措施是只读验证者。实现规则：

- 验证者与团队共享状态（读取黑板或池）。
- 验证者没有对共享状态的写入句柄——仅对独立的验证通道。
- 验证者独立重新获取写入中引用的来源。标记分歧。
- 验证者自己的输出被路由给人类或独立决策智能体，永不反馈回池中。

没有这种分离，验证者的输出成为池中的新条目，这意味着污染的池污染验证者，验证者污染其验证。

## 构建它

`code/main.py` 在标准库Python中实现两种拓扑，加上玩具污染攻击和三���缓解措施。

- `MessagePool`——带完整读出的线程安全仅追加日志。
- `Blackboard`——带每个智能体订阅的主题键值发布/订阅。
- `ProvenanceEntry`——每次写入记录（writer, timestamp, prompt_hash, source_uri）。
- `PoisoningScenario`——运行一个智能体A幻觉小数的三智能体研究任务。打印最终报告。
- `Verifier`——一个重新获取来源并标记不一致的只读智能体。在验证者存在下运行相同场景。

运行：

```
python3 code/main.py
```

预期输出：
- 运行1（无验证者）：幻觉42%传播到最终报告。
- 运行2（有验证者）：验证者标记不一致，池被标记为"flagged"，最终报告包含撤回。

## 运用

`outputs/skill-memory-auditor.md` 是一个技能，审计任何多智能体系统共享内存设计的来源、版本化和验证者分离。在生产前对新多智能体架构运行它。

## 交付物

对于任何共享内存设计：

- 在每次写入上记录来源：`(writer, timestamp, prompt_hash, tool_calls_cited, source_uri)`。
- 使日志仅追加。更正是引用被替代条目的新条目。
- 部署至少一个具有独立来源访问的只读验证者智能体。
- 将验证者输出路由到独立通道，而非回归共享池。
- 记录替代条目写入的比例——上升比例是幻觉模式的早期证据。

## 练习

1. 运行 `code/main.py`。确认运行1传播幻觉，运行2捕获它。
2. 添加第二个幻觉：智能体B发明一个数据集大小。验证者应捕获两者而无须为任一进行手工调优。
3. 将全池切换为带主题分区（`prices`、`summaries`、`analyses`）的黑板。主题分区使哪些污染场景更难成功，对哪些无帮助？

## 关键术语

| 术语 | 人们常说的 | 实际含义 |
|------|----------------|------------------------|
| 消息池 | "共享聊天历史" | 每个智能体读取的仅追加日志。完全透明，扩展性差。 |
| 黑板 | "共享工作空间" | 主题键值发布/订阅。智能体订阅相关主题。扩展更远。 |
| 来源 | "谁写了什么" | 每次写入的元数据：写入者、时间戳、提示、来源。 |
| 内存污染 | "幻觉传播" | 一个智能体的错误进入共享状态，下游智能体将其作为事实采纳。 |
| 仅追加 | "无就地更新" | 修正是替代的新条目。保留审计追踪。 |
| 不可写入的验证者 | "独立审计员" | 重新获取来源并标记不一致的只读智能体。 |
| 投影 | "限定视图" | 从全局状态计算的每个智能体视图。LangGraph reducer是权威案例。 |
| 知识源 | "专家智能体" | Hayes-Roth 1985年对黑板参与者的术语。 |
