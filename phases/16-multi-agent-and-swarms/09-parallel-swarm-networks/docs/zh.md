# 并行/群体/网络化架构

> 与监督者对比：没有中央决策者。智能体读取共享事件总线，异步拾取工作，将结果写回。LangGraph明确支持用于去中心化、动态环境的"群体架构"。Matrix（arXiv:2511.21686）将控制流和数据流都表示为序列化消息，通过分布式队列传递以消除编排者瓶颈。权衡是显式的：用确定性和可追踪性换取可扩展性。群体适合具有许多独立子问题的任务；它不适合需要单一连贯计划的任务。

**Type:** Learn + Build
**Languages:** Python (stdlib, `threading`, `queue`)
**Prerequisites:** Phase 16 · 05 (Supervisor Pattern), Phase 16 · 04 (Primitive Model)
**Time:** ~75 minutes

## 问题

监督者可以扩展到少数工作者。成百上千个呢？监督者本身成为瓶颈：每个关于谁做什么的决策都通过一个智能体集束。一个慢的规划步骤就使整个系统停滞。

群体架构翻转了设计。不是中央规划者分派工作，而是工作者从共享队列中拾取工作。"协调"被烘焙到事件总线语义中。没有编排者；系统随队列扩展。

## 概念

### 形状

```
                ┌──── 共享队列 ────┐
                │                      │
       ┌────────┼────────┐  ◄──────┬───┘
       ▼        ▼        ▼         │
     工作者   工作者   工作者   工作者
      A       B       C        D
       │        │        │         │
       └────────┴────────┴─────────┘
                 │
                 ▼
            结果池
```

没有编排者。每个工作者重复：拉取一个任务、处理、写入结果（并可选择入队后续任务）。

### 何时群体适合

- **许多独立任务。** 爬取、转换、分类。任务不互相依赖。
- **可变持续时间的工作。** 如果一些任务需要100ms而另一些需要10s，一个群体会自动平衡负载——快速工作者拉取下一个工作。监督者必须预期持续时间。
- **吞吐量优先于确定性。** 你关心总完成时间，而非严格排序。

### 何时群体失败

- **有序工作流。** 如果步骤3需要步骤2的输出，群体有步骤3在步骤2完成前触发的风险。
- **全局计划任务。** 复杂的研究问题受益于规划者。一个研究群体产生独立事实，而非连贯报告。
- **调试。** 没有中央日志和异步工作，重现Bug成本高昂。

### Matrix（arXiv:2511.21686）

Matrix是2025年将群体推向其自然结论的论文：控制流和数据流都是分布式队列上的序列化消息。没有中央协调器。故障容忍来自消息持久性。可扩展性是消息代理的问题，而非系统的。

贡献：一个编程模型，使多智能体协调成为"该智能体订阅什么消息主题？"而非"监督者下一个选择哪个智能体？"这使系统看起来像发布/订阅事件网格。

### LangGraph的群体架构

LangGraph 2025年文档明确将"群体架构"描述为多智能体模式之一：智能体是节点，但边形成有向图且带循环，任何节点都可以从池中被激活。工作者通过条件而非监督者分配从可用工作中拾取。

### 失败模式：饥饿和热点

如果所有工作者都拉取最快可用的任务，长时间运行的任务直到它们是唯一剩下的任务之前都不会被拾取。经典的队列饥饿。

缓解措施：
- 带显式老化的优先级队列（等待时间增加优先级）。
- 工作者专门化：一些工作者只接受"长"任务。
- 背压：限制多少快速任务进入队列。

### 基于内容的路由链接

群体自然与基于内容的路由配对（第22课）。不是通用队列，而是每种消息类型一个队列。专家工作者只订阅它们自己的类型。这是可扩展到数千智能体的消息总线架构的基础。

## 构建它

`code/main.py` 实现一个4个工作线程从共享的 `queue.Queue` 拉取任务的群体。任务具有变量持续时间（一些快，一些慢）。演示对比：

- **顺序基线：** 一个工作者串行处理所有任务。
- **固定分配：** 每个任务预先分配给特定工作者（监督者风格）。
- **群体：** 工作者从共享队列拉取。

群体自动平衡负载；固定分配在其分配的任务慢时让快速工作者空闲。

运行：

```
python3 code/main.py
```

输出显示每个工作者的任务计数（群体分配不均匀但最优）和墙钟时间。

## 运用

`outputs/skill-swarm-fit.md` 评估任务应使用群体还是监督者。输入：任务独立性、持续时间方差、排序要求、可调试性需求。

## 交付物

检查清单：

- **带老化的优先级队列。** 防止长任务饥饿。
- **工作者幂等性。** 如果工作者中途崩溃，任务可能被拉取多次。工作者必须是幂等的。
- **持久队列。** 对生产使用Kafka、Redis Streams或数据库支持的队列。`queue.Queue` 仅内存中。
- **每个任务的可观测性。** 每个任务有一个追踪ID；每个工作者用其记录开始/结束。
- **背压。** 如果队列增长速度超过工作者排空速度，减慢生产者。

## 练习

1. 运行 `code/main.py`。在可变持续时间工作负载上，群体比顺序快多少？比固定分配快多少？
2. 添加优先级队列变体（使用 `queue.PriorityQueue`）。按任务"重要性"字段分配优先级。观察在连续负载下低优先级任务是否永不饥饿。
3. 实现热点检测器：当任何工作者处理比最慢工作者多3倍以上的任务时记录日志。这对任务持续时间分布意味着什么？
4. 阅读Matrix论文（arXiv:2511.21686）摘要和第3节。识别Matrix接受的一个特定权衡（可扩展性收益）和它放弃的一个（可追踪性、确定性）。
5. 将群体演示转换为使用 `queue.Queue` 的 (task_type, payload) 元组，工作者仅订阅特定类型。当任务是异构的时，什么路由规则有意义？

## 关键术语

| 术语 | 人们常说的 | 实际含义 |
|------|----------------|------------------------|
| 群体架构 | "去中心化智能体" | 工作者从共享队列拉取；没有中央编排者。 |
| 事件总线 | "智能体订阅主题" | 按类型或内容将任务路由到工作者的消息代理。 |
| 饥饿 | "任务永不运行" | 低优先级任务永不拾取因为更高优先级的工作持续到达。 |
| 热点 | "一个工作者被淹没" | 负载不平衡，一个工作者获得大多数任务。 |
| 背压 | "减慢生产者" | 当队列填满时向上游发出停止产生的信号机制。 |
| 幂等工作者 | "安全重运行" | 处理两次的任务产生相同结果。需要因为工作者可能中途崩溃。 |
| 持久队列 | "在崩溃中存活" | 由磁盘或复制存储支持的队列；任务不在工作者崩溃时丢失。 |
| Matrix框架 | "全消息传递群体" | 数据和控制流都是分布式队列上的序列化消息。 |
