# 角色专门化——规划者、批评者、执行者、验证者

> 2026年最常见多智能体分解：一个智能体规划，一个执行，一个批评或验证。MetaGPT（arXiv:2308.00352）将此形式化为编码到角色提示中的SOP——产品经理、架构师、项目经理、工程师、QA工程师——遵循 `Code = SOP(Team)`。ChatDev（arXiv:2307.07924）链接设计师、程序员、审阅者、测试者，通过带有"沟通去幻觉化"的"聊天链"（智能体显式请求缺失的细节）。验证者是承重的：Cemri等人（MAST，arXiv:2503.13657）显示每个多智能体失败都可以追溯到缺失或破损的验证。PwC报告在CrewAI中结构化验证循环带来7倍准确率提升（10% → 70%）。

**Type:** Learn + Build
**Languages:** Python (stdlib)
**Prerequisites:** Phase 16 · 04 (Primitive Model), Phase 16 · 05 (Supervisor)
**Time:** ~60 minutes

## 问题

泛型多智能体系统产生泛型输出。群组聊天中的三个编码者写出相同平庸代码的三种变体。你可以添加更多智能体，添加更多轮次，仍然不能越过质量阈值。

修复方案不是更多智能体——是*不同*的智能体。分配不同的角色。给批评者规划者没有的工具。给验证者一个客观的测试套件。现在系统有了带有基于实际纠正的内部分歧，而不仅仅是并行猜测。

## 概念

### 四种规范角色

**规划者。** 读取目标，产生步骤列表或规范。工具：知识检索、文档。输出：结构化计划。

**执行者。** 一次读取一个计划步骤，产生产物。工具：实际的工作工具（代码编译器、Shell、API客户端）。输出：产物。

**批评者。** 根据规划者的意图读取执行者的输出。工具：对产物的只读访问、静态分析。输出：带理由的接受/拒绝。

**验证者。** 读取产物并运行确定性检查。工具：测试运行器、类型检查器、模式验证器。输出：带证据的通过/失败。

批评者是主观的、有意见的，通常基于LLM。验证者是客观的、确定性的，通常基于代码。它们不是同一个角色。

### MetaGPT的SOP模式

MetaGPT（arXiv:2308.00352）将软件工程SOP编码为角色提示：

- **产品经理** 编写PRD。
- **架构师** 产生系统设计。
- **项目管理者** 拆分任务。
- **工程师** 实现。
- **QA工程师** 运行测试。

每个角色都有严格的输入/输出模式。角色提示说明该角色*是什么*以及它*必须产生什么*。`Code = SOP(Team)` 表述——确定性SOP将LLM团队转变为可预测的流水线。

### ChatDev的沟通去幻觉化

ChatDev添加了一个关键动作：当执行者需要计划中没有的特定细节时，它在继续之前显式询问设计者。这防止了经典LLM失败：合理编造细节。

实现：角色提示包含"当你需要你未被给予的特定信息时，在产生输出之前按名称询问相关角色。"

### 为什么验证者最重要

Cemri等人（MAST）追踪了1642次多智能体执行失败。21.3%是验证差距——系统交付了一个无人检查的答案。剩余的79%通常追溯到"有一个检查静默失败或从未运行。"验证是承重角色。

PwC报告（CrewAI部署，2025年）添加结构化验证循环将准确率从10%提升到70%。一个角色带来7倍增益。

### 批评者 vs 验证者

- 批评者是LLM审查产物的质量。主观。可能被合理的文字欺骗。
- 验证者是运行在产物上的确定性程序。客观。给出带证据的通过/失败。

使用两者。批评者捕获验证者无法表达的品味问题。验证者捕获批评者看不到的Bug，因为它们只在运行时出现。

### 反模式

你系统中的每个角色都是LLM，每个角色的输出都是"看起来不错。"经典MAST失败模式。添加至少一个其通过/失败由代码决定的验证者，而非LLM。

### 框架映射

- **CrewAI**——`Agent(role, goal, backstory)` 是教科书的专门化表面。
- **LangGraph**——节点可以有专门化提示；边强制执行流水线。
- **AutoGen**——GroupChat中具有一个词名称的角色特定ConversableAgents。
- **OpenAI Agents SDK**——角色专门化Agents之间的移交工具。

## 构建它

`code/main.py` 实现一个构建简单Python函数的4角色流水线：

- **规划者**产生规范。
- **执行者**生成代码字符串。
- **批评者**（LLM模拟）标记明显问题。
- **验证者**在沙盒中运行生成的代码（`exec`）进行测试案例验证。

演示运行两次：一次执行者产生正确代码（批评者 + 验证者都通过），一次执行者产生偏离规范的代码（批评者错过Bug因为它看起来合理，验证者捕获它因为测试失败）。

运行：

```
python3 code/main.py
```

## 运用

`outputs/skill-role-designer.md` 接收任务并生成角色名册（3-5个角色）、每个角色的输入/输出模式以及验证者检查。在将智能体连接到框架之前使用此技能。

## 交付物

检查清单：

- **至少一个确定性验证者。** 绝不全部是LLM。
- **每个角色的显式I/O模式。** 规划者返回规范，而非散文；执行者读取该模式。
- **沟通去幻觉化。** 执行者必须在信息缺失时询问规划者；绝不编造它。
- **批评者/验证者排序。** 先运行批评者（便宜，捕获设计问题），验证者其次（慢，捕获Bug）。
- **循环预算。** 在升级到人类之前最多2轮批评者-执行者修订轮次。

## 练习

1. 运行 `code/main.py` 并观察验证者如何捕获批评者错过的Bug。添加静态分析检查（计数 `return` 出现次数）作为额外的验证者。它捕获了运行测试遗漏的什么？
2. 添加第5个角色："需求分析师"，将用户愿望翻译为规划者就绪的规范。什么沟通去幻觉化请求应该向上流向它？
3. 阅读MetaGPT第3节（"Agents"）。列出MetaGPT的5个角色各自的输入/输出模式。
4. 阅读ChatDev的聊天链图（arXiv:2307.07924 图3）。确认沟通去幻觉化在哪里打破了否则会是无限的循环。
5. PwC的7倍准确率增长来自验证循环。假设三个添加验证者不会有帮助的任务——其中对正确性的确定性检查不可能或禁止性昂贵。

## 关键术语

| 术语 | 人们常说的 | 实际含义 |
|------|----------------|------------------------|
| 角色专门化 | "不同智能体，不同工作" | 为规划者/执行者/批评者/验证者角色调优的独立系统提示。 |
| SOP模式 | "编码的标准操作流程" | MetaGPT的框架：每个角色的严格I/O模式将团队转变为流水线。 |
| 沟通去幻觉化 | "询问而非编造" | ChatDev模式：执行者在细节缺失时询问规划者而非编造一个。 |
| 批评者 | "LLM审阅者" | 主观、有意见的审阅者。捕获品味问题。可能被合理的文字欺骗。 |
| 验证者 | "确定性检查" | 基于代码的通过/失败。测试运行器、类型检查器、模式验证器。无法被欺骗。 |
| 验证差距 | "无人检查" | 21.3%的MAST失败。答案交付时没有会捕获Bug的检查。 |
| 修订循环 | "批评者发回修改" | 批评者拒绝触发执行者带反馈重新运行。需要预算。 |
| 全LLM反模式 | "看起来不错" | 每个角色都是LLM，没有确定性检查。经典MAST失败。 |
