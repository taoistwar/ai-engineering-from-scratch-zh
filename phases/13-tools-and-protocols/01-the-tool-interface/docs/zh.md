# 工具接口——为什么代理需要结构化 I/O

> 语言模型产生 token。程序执行动作。两者之间的间隙就是工具接口：一个让模型请求动作、宿主执行动作的契约。每个 2026 年技术栈——OpenAI、Anthropic 和 Gemini 上的 function calling；MCP 的 `tools/call`；A2A 的任务部件——都是这相同的四步循环的不同编码形式。本课命名这个循环，并展示运行它的最小机制。

**Type:** Learn
**Languages:** Python (stdlib, no LLM)
**Prerequisites:** Phase 11 (LLM completion APIs)
**Time:** ~45 minutes

## 学习目标

- 解释为什么一个只能生成文本的 LLM 自身无法对真实世界执行动作。
- 画出四步工具调用循环（描述 → 决定 → 执行 → 观察）并指出每一步由谁负责。
- 将工具描述写成三部分：名称、JSON Schema 输入和一个确定性的执行器函数。
- 区分纯工具与有副作用的工具，并说明为什么这种区分对安全性很重要。

## 问题

LLM 发出对下一个 token 的概率分布。这就是全部的输出接口。如果你问聊天模型"现在班加罗尔的天气如何"，它可以写出一个合理的句子，但它无法接入天气 API。这个句子可能巧合正确，也可能已经过时三天。

弥合这个差距就是工具接口的目的。宿主程序——你的代理运行时、Claude Desktop、ChatGPT、Cursor 或自定义脚本——向模型公告一个可调用工具的列表。模型在决定需要某个动作时，发出一个结构化载荷，指定工具名称及其参数。宿主解析该载荷，真实地运行工具，并将结果反馈回去。循环持续到模型决定不需要更多调用为止。

这个契约的第一个版本于 2023 年 6 月作为 OpenAI 的 "functions" 参数发布。Anthropic 在 Claude 2.1 中以 `tool_use` 块跟进。几个月后 Gemini 增加了 `functionDeclarations`。现在每个提供商都暴露相同的形状：JSON Schema 类型的工具列表作为输入，JSON 载荷的工具调用作为输出。Model Context Protocol（2024 年 11 月）泛化了这个契约，使一个工具注册表可以服务所有模型。A2A（2026 年 4 月，v1.0）为代理到代理委托分层构建了相同的原语。

四步循环是所有这些之下的不变量。Phase 13 中的其他所有内容都是在此基础上的详细展开。

## 概念

### 步骤一：描述

宿主用三个字段声明每个工具。

- **名称。** 一个稳定的、机器可读的标识符。`get_weather`，而非 "weather thing"。
- **描述。** 一段自然语言的简要说明。"当用户询问特定城市当前天气状况时使用。不要用于历史数据。"
- **输入 schema。** 描述工具参数的 JSON Schema 对象（draft 2020-12）。

模型接收这个列表。现代提供商将这些声明序列化到系统提示中，使用提供商特定的模板，因此作为调用方你只需处理结构化形式。

### 步骤二：决定

给定用户消息和可用工具，模型选择三种行为之一。

1. **直接以文本回答。** 不进行工具调用。
2. **调用一个或多个工具。** 发出结构化调用对象。在 `parallel_tool_calls: true` 下（OpenAI 和 Gemini 默认，Anthropic 需选择加入），模型可以在一个回合中发出多个调用。
3. **拒绝。** 严格模式的结构化输出可以产生一个类型化的 `refusal` 块而非调用。

工具调用载荷有三个稳定字段：调用 `id`、工具 `name` 和 JSON `arguments` 对象。id 存在是为了宿主能够将后续结果与特定调用关联起来，这在并行调用乱序返回时很重要。

### 步骤三：执行

宿主接收调用，根据声明的 schema 验证参数，并运行执行器。无效参数意味着模型虚构了一个字段或使用了错误的类型——这是在弱模型上非常常见的失败模式。生产级宿主对无效参数做三件事之一：快速失败并将错误暴露给模型，使用受限解析器修复 JSON，或将验证错误包含在提示中重试模型。

执行器本身是普通代码。Python、TypeScript、一个 shell 命令、一个数据库查询。它产生一个结果，通常是字符串，但可以是任何 JSON 值或结构化内容块（MCP 中的文本、图像或资源引用）。结果必须是可序列化的。

### 步骤四：观察

宿主将工具结果追加到对话中（作为具有匹配 `id` 的 `tool` 角色消息）并重新调用模型。模型现在具有上下文中的工具输出，可以产生最终答案或请求更多调用。这持续到模型停止发出调用或宿主达到迭代次数的安全限制。

### 信任划分

工具在安全性方面分为两类。

- **纯工具。** 只读、确定性、无副作用。`get_weather`、`search_docs`、`get_current_time`。可以推测性地安全调用。
- **后果性工具。** 改变状态、花费金钱、触碰用户数据。`send_email`、`delete_file`、`execute_trade`。必须加以门控。

Meta 2026 年代理安全的"二法则"（Rule of Two）指出，单次回合最多可组合其中两项：不可信输入、敏感数据、后果性动作。工具接口正是你执行该规则的地方——通过拒绝调用、要求用户确认或提升权限范围。完整安全章节见 Phase 13 · 15，代理级权限策略见 Phase 14 · 09。

### 循环存在于何处

| 上下文 | 谁描述 | 谁决定 | 谁执行 |
|---------|--------|--------|--------|
| 单次回合 function calling（OpenAI/Anthropic/Gemini） | 应用开发者 | LLM | 应用开发者 |
| MCP | MCP 服务器 | LLM 通过 MCP 客户端 | MCP 服务器 |
| A2A | Agent Card 发布者 | 调用代理 | 被调用代理 |
| 网页浏览器（function-calling 代理） | 浏览器扩展 / WebMCP | LLM | 浏览器运行时 |

无论何处，相同的四步。列名会变；结构不会。

### 为什么不直接提示模型输出 JSON？

"要求模型以 JSON 回复"是 function calling 之前的模式。在前沿模型上大约有 5% 到 15% 的失败率，在较小模型上则高得多。失败模式包括缺失花括号、尾部逗号、虚构字段和错误类型。然后你需要 JSON 修复、重试或受限解码器。

原生 function calling 更好，有三个原因。第一，提供商端到端地在精确的调用形状上训练模型，因此有效 JSON 率在严格模式下上升到 98% 到 99%。第二，调用载荷位于其自己的协议槽中，不在自由文本中——因此工具调用不会泄露到用户可见的回复中。第三，提供商通过受限解码（OpenAI 的严格模式、Anthropic 的 `tool_use`、Gemini 的 `responseSchema`）强制 schema 合规。输出是保证有效的。

Phase 13 · 02 将并排讲解三家提供商的 API。Phase 13 · 04 深入探讨结构化输出。

### 熔断器

当模型停止发出调用或宿主达到最大回合计数时，循环终止。生产级宿主通常设置为 5 到 20 个回合。超过这个数，几乎肯定陷入了模型无法退出的循环。Claude Code 默认为 20；OpenAI Assistants 为 10；Cursor 的代理模式为 25。

替代方案——无界循环——每六个月就会出现一次"代理在一夜之间消耗了 400 美元 API 调用"的事后分析。不要在未设置边界的情况下发布。

## 使用

`code/main.py` 在没有 LLM 的情况下运行四步循环。一个假的"决定者"函数通过对用户消息进行模式匹配来模拟模型；执行器、schema 验证器和观察步骤都是真实的。运行它以查看完整的请求/响应编排，并可打印中间状态，然后在后续课程中将假的决定者替换为任何真实的提供商。

需要注意的地方：

- 工具注册表为每个工具持有三个字段：名称、描述、schema 和一个执行器引用。
- 验证器是一个最小化的 JSON Schema 子集（类型、required、enum、min/max），仅用标准库编写。Phase 13 · 04 提供更完整的版本。
- 循环将迭代次数限制为五。生产代理想需要的就是这种熔断器。

## 产出

本课产出 `outputs/skill-tool-interface-reviewer.md`。给定一份工具定义草案（名称 + 描述 + schema + 执行器大纲），该技能审核其循环适应性：名称是否机器稳定，描述是否是完整的使用说明，schema 是否正确使用了 JSON Schema 2020-12，以及纯工具 vs 后果性工具的分类是否明确。

## 练习

1. 向 `code/main.py` 中添加第四个工具 `get_stock_price(ticker)`。将其描述写为"当用户通过股票代码询问当前股价时使用。不要用于历史价格或市场摘要。"运行框架并确认假的决定者将提到股票代码的查询路由到新工具。

2. 让 schema 验证器失败。传递一个 `arguments` 对象缺少必需字段的调用，确认宿主在执行前拒绝它。然后传递一个带有额外未知字段的调用。决定：宿主应该拒绝还是忽略？用安全论点证明你的选择。

3. 将框架中的每个工具分类为纯工具或后果性工具。向需要的注册表条目添加 `consequential: true` 标志，并修改循环，在选择了后果性工具时打印"会与用户确认"的行。这就是每个生产宿主需要的确认门控的形式。

4. 在纸上画出四步循环，并为你最喜欢的客户端（Claude Desktop、Cursor、ChatGPT 或自定义技术栈）填入上面的提供商列表示例图。与 Phase 13 · 06 中的 MCP 特定变体进行交叉引用。

5. 从上到下阅读 OpenAI 的 function-calling 指南。指出请求中存在但此处介绍的四步循环中不存在的一个字段。解释它添加了什么，以及为什么它方便而不是必需的。

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|-----------|---------|
| 工具 | "模型可以调用的东西" | 名称 + JSON Schema 类型输入 + 执行器函数的三元组 |
| Function calling | "原生工具使用" | 提供商级别的 API 支持，用于发出结构化工具调用而非散文 |
| 工具调用 | "模型发出的动作请求" | 由模型发出的带有 `id`、`name`、`arguments` 的 JSON 载荷 |
| 工具结果 | "工具返回了什么" | 执行器的输出，包装在具有匹配 id 的 `tool` 角色消息中 |
| 并行工具调用 | "一次发出多个调用" | 一个模型回合中的多个调用对象，独立且可通过 id 排序 |
| 严格模式 | "保证 JSON" | 受限解码，强制模型的输出针对声明的 schema 进行验证 |
| 纯工具 | "只读工具" | 无副作用；可以安全地重新运行 |
| 后果性工具 | "动作工具" | 改变外部状态；需要门控、审计或用户确认 |
| 四步循环 | "工具调用周期" | 描述 → 决定 → 执行 → 观察 |
| 宿主 | "代理运行时" | 持有工具注册表、调用模型并运行执行器的程序 |
