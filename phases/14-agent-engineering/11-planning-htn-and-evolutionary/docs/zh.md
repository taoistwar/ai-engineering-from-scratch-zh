# HTN 与进化搜索规划

> 符号规划处理计划可被证明正确的情况。进化代码搜索处理适应度函数可被机器检查的情况。ChatHTN（2025）和 AlphaEvolve（2025）展示了每个在与 LLM 配对时能解锁什么。

**类型:** Build
**语言:** Python（标准库）
**前置要求:** Phase 14 · 02（ReWOO 与 Plan-and-Execute）
**时间:** ~75 分钟

## 学习目标

- 解释层次任务网络：任务、方法、操作符、前置条件、效果。
- 描述 ChatHTN 的混合循环——带有 LLM 回退分解的符号搜索。
- 解释 AlphaEvolve 的进化循环以及为什么它只在有程序化评估器时才能工作。
- 在标准库中实现一个玩具 HTN 规划器加上一个玩具进化搜索。

## 问题

ReWOO（第 02 课）、Plan-and-Execute 和 ReAct 覆盖了大多数 agent 规划。它们不能很好覆盖的两种情况：

1. **具有可证明正确性的计划。** 调度、飞行路径规划、合规工作流——计划必须通过构造即是正确的。一个流利但有时幻觉步骤的 LLM 计划是不可接受的。
2. **具有机器可检查适应度函数的优化。** 矩阵乘法、调度启发式、编译器遍——目标不是"一个正确的计划"而是"最佳计划"。

HTN 规划和 AlphaEvolve 解决了这两个不同的问题。两者都将 LLM 作为放大器而非替代品使用。

## 概念

### 层次任务网络

一个 HTN 是：

- **任务（Tasks）** — 复合（待分解）和原始（可直接执行）。
- **方法（Methods）** — 将复合任务分解为子任务的方式，带有前置条件。
- **操作符（Operators）** — 带有前置条件和效果的原始动作。
- **状态（State）** — 一组事实。

规划：给定一个目标任务和一个初始状态，找到分解为原始操作符的方案，使其前置条件按顺序得到满足。

HTN 比 LLM 更古老，且仍然是可证明正确规划的参考标准。

### ChatHTN（Gopalakrishnan et al., 2025）

ChatHTN（arXiv:2505.11814）将符号 HTN 与 LLM 查询交织：

1. 尝试用现有方法分解当前的复合任务。
2. 如果没有方法适用，询问 LLM："你会如何在状态 `s` 中分解 `task`？"
3. 将 LLM 响应转化为候选子任务。
4. 根据操作符模式进行验证；拒绝无效分解。
5. 递归。

论文的核心主张：产生的每个计划都是可证明正确的，因为 LLM 建议仅作为候选分解进入，从不作为直接的计划编辑。符号层拥有正确性；LLM 扩展方法库。

在线方法学习（OpenReview `gwYEDY9j2x`，2025 年后续）增加了一个学习器，通过回归泛化 LLM 产生的分解——最多减少 75% 的 LLM 查询频率。

### AlphaEvolve（Novikov et al., 2025）

AlphaEvolve（arXiv:2506.13131，DeepMind，2025 年 6 月）是另一个物种：由 Gemini 2.0 Flash/Pro 集合编排的进化代码搜索。

循环：

1. 从种子程序 + 程序化评估器开始（返回适应度分数）。
2. LLM 集合提议突变。
3. 通过评估器运行突变。
4. 保留最佳；再次突变。

已发布的胜果：

- 56 年来首次对 4x4 复数矩阵乘法的 Strassen 改进（48 次标量乘法）。
- 通过 Borg 调度启发式恢复了 0.7% 的 Google 计算资源。
- 在某个前沿工作负载上获得 32% 的 FlashAttention 加速。

硬约束：适应度函数必须是机器可检查的。对散文答案的进化搜索不会收敛。

### 何时使用哪种

| 问题类别 | 使用 | 为什么 |
|---------------|-----|-----|
| 具有硬约束的调度 | HTN + ChatHTN | 可证明的正确性 |
| 编译器优化 | AlphaEvolve | 机器可检查的适应度 |
| 多步任务执行 | ReAct / ReWOO | LLM 在循环中，无形式化保证 |
| 带测试的代码改进 | AlphaEvolve | 测试就是评估器 |
| 策略约束的自动化 | HTN | 前置条件编码策略 |

### 此模式在哪些情况下会出错

- **没有操作符的 HTN。** 没有前置条件/效果模式，正确性主张会崩溃。ChatHTN 的"LLM 建议分解"需要模式来拒绝无效移动。
- **没有真正评估器的 AlphaEvolve。** "问 LLM 代码是否更好"不是适应度函数。评估器必须是确定性的且快速的。
- **过度工程。** 大多数 agent 任务不需要这两种方案。首先伸手拿 ReAct 或 ReWOO。

## Build It

`code/main.py` 实现两个玩具：

- 一个标准库 HTN 规划器，包含操作符、方法、前置条件、效果，以及一个 `LLMFallback`，当没有方法匹配复合任务时介入。"LLM" 是一个脚本化分解器，这样规划器可以离线运行。
- 一个对算术程序的标准库进化搜索：生长其输出在测试集上最小化 `|f(x) - target|` 的表达式。评估器是确定性的。

运行它：

```
python3 code/main.py
```

追踪显示 HTN 规划器分解一个复合任务（中间有 LLM 回退），以及进化循环收敛到一个目标表达式。

## Use It

- **HTN 规划器** — `pyhop`、`SHOP3`，或为领域特定策略强制执行构建自己的。
- **ChatHTN** — 研究代码；该模式（符号 + LLM 回退）可干净地移植到任何 HTN 规划器。
- **AlphaEvolve** — DeepMind 论文；该模式（集合 + 评估器）是可复现的。OpenEvolve 和类似的开源分支正在涌现。
- **Agent 框架** — 目前没有框架提供一等的 HTN 或 AlphaEvolve。作为子 agent 或后台 worker 构建它。

## Ship It

`outputs/skill-hybrid-planner.md` 生成一个混合规划器脚手架（HTN 或进化），LLM 角色显式限定范围。

## 练习

1. 用回溯扩展 HTN 规划器：当操作符的运行时后置条件失败时，回滚并尝试下一个方法。
2. 为 ChatHTN 添加 LLM 方法缓存：当 LLM 在状态模式 `P` 中分解任务 `T` 时，存储结果。下次调用时先检查方法库。
3. 将进化搜索评估器替换为真实测试套件。进化一个能通过 20 个测试用例的排序函数；报告到收敛所需的代数。
4. 阅读 AlphaEvolve 的评估器设计说明。为你关心的领域设计评估器（SQL 查询优化、测试套件最小化、部署 YAML）。
5. 结合使用：用 HTN 将复合任务分解为子任务，然后在每个子任务的原始操作符上使用进化搜索。它在哪里发光，在哪里过度工程？

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|----------------|------------------------|
| HTN | "层次规划器" | 带有操作符、前置条件、效果的任务分解 |
| 方法 | "分解规则" | 将复合任务分解为子任务的方式 |
| 操作符 | "原始动作" | 带有前置条件和效果的具体步骤 |
| ChatHTN | "LLM + HTN" | 当没有方法匹配时符号规划器询问 LLM |
| AlphaEvolve | "进化代码搜索" | LLM 集合突变代码；确定性评估器选择 |
| 适应度函数 | "评估器" | 对输出的确定性、机器可检查的分数 |
| 在线方法学习 | "缓存的 LLM 分解" | 存储 + 泛化 LLM 计划以减少查询成本 |
