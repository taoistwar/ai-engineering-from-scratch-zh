# 百万 Token 上下文下的长视频理解

> 一段以 24 FPS 录制的 1 小时 4K 视频，经过 patch 和嵌入，产生大约 6000 万个 token。一段转录的 2 小时播客是 30,000 个 token。一部完整的蓝光电影，即使通过激进的池化进行压缩，也有数十万个 token。Google 的 Gemini 1.5（2024 年 3 月）以 1000 万 token 上下文开启了这个时代，在数小时长的视频上可靠地进行大海捞针式回忆。LWM（Liu 等人，2024 年 2 月）展示了 ring attention 的扩展路径。LongVILA 和 Video-XL 进一步扩大了输入规模。VideoAgent 用代理式检索替换了原始上下文。每种方法都是在计算、回忆和工程复杂度之间的不同权衡。本课将它们放在一起阅读。

**Type:** Build
**Languages:** Python (stdlib, needle-in-haystack simulator + agentic-retrieval router)
**Prerequisites:** Phase 12 · 17 (video temporal tokens)
**Time:** ~180 minutes

## 学习目标

- 在不同 FPS 和池化下计算长视频的总视觉 token 数。
- 解释三种扩展路径：暴力上下文（Gemini 1.5）、ring attention（LWM）、token 压缩（LongVILA / Video-XL）。
- 在准确率和延迟上比较原始上下文视频 VLM vs 代理式检索视频 VLM（VideoAgent）。
- 为 30 分钟的视频设计一个大捞针测试，并测量在特定分钟处的回忆率。

## 问题

一帧 Qwen2.5-VL 大小 patch、384 原生分辨率下的画面约为 729 个 token。使用 3x3 池化后每帧 81 个 token。一段 30 分钟的 1 FPS 片段 = 1800 帧 = 145,800 个 token。2025 年开源 VLM 可行，但很紧。在 2 FPS 下，291,600 个 token——只有最大的上下文能容纳。

一部 2 小时的电影以 1 FPS 是 583k 个 token。超出大多数 2026 年开源模型的能力；需要 Gemini 2.5 Pro 或更激进的池化。

出现了三种扩展路径。

## 概念

### 路径 1：暴力上下文（Gemini 1.5、Claude Opus）

用硬件堆问题。将上下文扩展到数百万 token，在一次前向传播中处理所有内容。

Gemini 1.5 Pro 以 1M token 发布；Gemini 1.5 Ultra 达到 10M；2026 年的 Gemini 2.5 Pro 能可靠处理数小时的视频。论文（arXiv:2403.05530）记录了高达约 9.5M token 的 99.7% 大海捞针回忆率。

工程：一种带有内存层次结构（局部 + 全局 + 稀疏）的自定义注意力实现，加上用于长上下文效率的 MoE 专家路由。未公开完整细节。不开源。

### 路径 2：Ring attention（LWM、LongVILA）

Ring attention 将长序列分布到以"环"形式排列的设备上，每个设备持有一个块。完整序列上的注意力通过每个设备将其块发送到环中的下一个设备，计算部分注意力，并进行聚合。

LWM（Liu 等人，2024）以这种方式训练了一个 1M token 上下文模型。训练计算量随上下文线性扩展，而非二次方——注意力的二次方开销被环上的设备分散。

LongVILA（arXiv:2408.10188）将该模式适配到 VLM。1400 帧视频、每帧 192 个 token = 268k 上下文，通过 8 路并行的 ring attention 进行训练。

### 路径 3：Token 压缩（Video-XL、LongVA）

比暴力上下文更便宜：在 LLM 看到序列之前激进地压缩。

Video-XL（arXiv:2409.14485）使用视觉摘要 token：N 帧的每个片段产生一个单一的"摘要"token，该 token 关注这 N 帧。在推理时，LLM 每个片段看到一个摘要 token，极大地缩小了上下文。

LongVA 通过"长上下文迁移"技术将 LLM 上下文从 200k 扩展到 2M。在长上下文文本上训练，通过共享表示迁移到长上下文视频。

Token 压缩以在特定时间戳的召回率为代价换取可扩展性。模型大致知道发生了什么，但有时会错过确切的帧。

### 路径 4：代理式检索（VideoAgent）

不要将完整视频馈送给 LLM。相反，将视频视为数据库，使用 LLM 查询它。

VideoAgent（arXiv:2403.10517）：

1. LLM 读取问题。
2. LLM 请求检索工具获取相关片段（"显示有猫的段落"）。
3. 工具返回匹配的片段时间戳。
4. LLM 通过 VLM 读取这些片段。
5. LLM 组成答案或发起后续查询。

这是应用于长视频的以 LLM 为代理模式。推理更便宜（仅编码相关片段），工程更困难（检索质量成为瓶颈）。

### 大海捞针基准

标准的长上下文测试：在视频中的随机点插入一个独特的视觉或文本标记，然后提出一个需要回忆它的查询。

指标：在视频长度和标记位置上的回忆率@k。

Gemini 2.5 Pro 在长达 90 分钟的视频中得分 >99% 的回忆率。开源 72B 模型（Qwen2.5-VL-72B、InternVL3-78B）在 30 分钟处得分约 85-90%，并在 60 分钟后下降。

在 2+ 小时的内容上，VideoAgent 可以匹敌或击败原始上下文模型，因为如果工具够好，检索能命中针。

### 选择哪条路径

对于 15 分钟片段达到前沿精度：开源 72B + 原生上下文通常可行。选择 Qwen2.5-VL-72B。

对于 30 分钟到 1 小时内容：开源选 LongVILA 或 Video-XL；闭源选 Gemini 2.5 Pro。质量基准很重要——前沿走闭源。

对于 2+ 小时内容：VideoAgent 或类似检索模式。或者，摘要为较小块并馈送分层摘要。

### 2026 年生产模式

在实践中，生产长视频管道是混合的：

1. 对整个视频运行动态 FPS 采样 + 激进池化（获得 100k token 的全局表示）。
2. 传递给 72B VLM 进行全局摘要。
3. 如果用户问详细问题，使用摘要作为索引运行代理式检索。

这结合了暴力上下文用于全局理解，以及检索用于局部细节。

## 使用

`code/main.py`：

- 计算从 1 分钟到 3 小时的视频在不同 FPS + 池化下的 token 预算。
- 模拟大海捞针运行：在随机时间戳注入标记，提出问题，计算回忆率。
- 包含一个代理式检索路由器模拟器，选择特定片段馈送给下游 VLM。

运行预算表并感受规模差距。

## 产出

本课产出 `outputs/skill-long-video-strategy-planner.md`。给定视频时长和查询复杂度，它在暴力上下文、压缩和代理式检索之间做出选择，并计算延迟 + 质量预期。

## 练习

1. 一段 45 分钟的讲座以 1 FPS、每帧 81 个 token 计算。总共多少个 token？能放入哪些模型的上下文？

2. 设计一个大捞针测试：在哪一分钟注入标记，确切的查询格式是什么？

3. 比较暴力上下文的 Qwen2.5-VL-72B（80k 上下文）与 VideoAgent（Claude 3.5 + 检索）在 1 小时视频上的表现。哪个在回忆上胜出？哪个在延迟上胜出？

4. Ring attention 的内存成本在序列长度和设备数量上都是线性扩展的。解释为什么，以及如果去掉环旋转阶段会出什么问题。

5. 阅读 Gemini 1.5 第 5 节关于大海捞针的内容。论文在 1M vs 10M token 边界上关于回忆率发现了什么？

## 关键术语

| 术语 | 人们怎么说 | 实际含义 |
|------|-----------|---------|
| 暴力上下文 | "就更多的 token" | 将 LLM 上下文扩展到数百万 token；在一次传递中处理所有内容 |
| Ring attention | "LWM 风格并行" | 分布式注意力模式，每个设备持有一个块并进行旋转 |
| Token 压缩 | "摘要 token" | 在 LLM 之前通过学习的压缩器减少每个片段的 token 数 |
| 大海捞针 | "NIH 测试" | 在随机点插入一个独特标记，在测试时要求模型回忆它 |
| 代理式检索 | "LLM 作为查询规划器" | LLM 请求检索工具获取相关片段，通过 VLM 读取它们，组成答案 |
| VideoAgent | "视频的检索模式" | 典型的代理式检索设计：问题 → 工具 → 片段 → 答案 |
