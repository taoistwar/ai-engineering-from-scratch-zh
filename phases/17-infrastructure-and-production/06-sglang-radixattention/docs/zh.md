# SGLang 和 RadixAttention 用于前缀密集型工作负载

> SGLang 将 KV 缓存视为存储在基数树中的一等可重用资源。vLLM 按 FCFS（先到先服务）调度请求，而 SGLang 的缓存感知调度器优先处理具有更长共享前缀的请求 — 实际上是一种深度优先的基数遍历，使热分支保留在 HBM 中。在 Llama 3.1 8B 上使用 ShareGPT 风格的 1K 提示，SGLang 达到 ~16,200 tok/s，对比 vLLM 的 ~12,500，约 29% 的优势。在前缀密集的 RAG 工作负载上，优势可达 6.4 倍。在语音克隆形状的工作负载上缓存命中率突破 86%。2026 年部署超过 400,000+ GPU，覆盖 xAI、LinkedIn、Cursor、Oracle、GCP、Azure、AWS。陷阱是当提示顺序不一致时，6.4 倍的数字蒸发了 — 顺序是工程师的杠杆。

## 学习目标

- 画图解释 RadixAttention：前缀如何存储在基数树中，以及 KV 块如何在具有相同分支的序列间共享。
- 解释缓存感知调度以及为什么 FCFS 对于前缀密集流量是错误的。
- 给定前缀缓存命中率和提示长度分布，计算工作负载的预期加速比。
- 说出使 6.4 倍数字成为现实而非损失的提示顺序规则。

## 问题

经典推理将每个请求的提示视为不透明的。即使 5,000 个 RAG 请求都以相同的 2,000 token 系统提示加上相同的检索前言开始，vLLM 也会将该 2,000 token 的前缀预填充 5,000 次。GPU 一遍又一遍地做同样的工作。

观察：在代理和 RAG 工作负载中，提示几乎总是共享长前缀。系统提示、工具模式、少样本示例、检索头、对话历史 — 都在请求间重复。如果你存储该前缀的 KV 缓存一次并重用它，你就不会再预填充它。

RadixAttention 正是这样做的。Token 在基数树中建立索引；每个节点拥有其从根路径上 token 序列的 KV 块。一个新请求在树中遍历：任何 token 匹配的节点重用该节点的 KV 块。预填充成本变为与"新"后缀成正比，而非完整提示。

挑战在于调度。如果两个请求共享 2,000 token 前缀，第三个只共享同一前缀的 200 token，你希望将两个長共享请求一起服务，使長前缀保留在 HBM 中。FCFS 做相反的事情 — 先服务先到达的请求，可能在下个長前缀请求到达之前驱逐热分支。

## 概念

### 基数树作为 KV 索引

基数树（压缩字典树）存储 token 序列。每个节点拥有一个 token 范围和为该范围计算的 KV 块。子节点扩展序列一个或多个 token。

```
root
 |- "You are a helpful assistant..."  (2,000 tokens, 124 KV blocks)
      |- "Context: <doc A>..."        (500 tokens, 31 blocks)
           |- "Question: Alice..."    (80 tokens, 5 blocks)
           |- "Question: Bob..."      (95 tokens, 6 blocks)
      |- "Context: <doc B>..."        (520 tokens, 33 blocks)
```

一个新请求带着系统提示 + "Context: <doc A>" + "Question: Carol" 到来。调度器遍历：系统前缀匹配（重用 124 块），doc-A 分支匹配（重用 31 块），然后仅为 "Question: Carol" 分配新块（4 块）。预填充成本：4 块新 token。没有树：160 块。约 40 倍预填充节省。

### 缓存感知调度

如果缓存不断被替换，基数树支持的重用是没有意义的。两个关键策略：

1. **深度优先分发**。从队列中选取下一个请求时，优先选择根在当前运行集合相同分支的请求。这使热分支保持驻留。
2. **分支级别的 LRU，而非块级别**。驱逐整个分支（从最短使用的叶子开始），而非单个块，使缓存形状与基数形状匹配。

FCFS 违反了两者。一个共享 2,000 token 的请求排在共享 50 token 的请求后面，然后 2,000 token 的分支被驱逐以容纳 50 token 的分支。

### 你应该记住的基准数字

- Llama 3.1 8B，H100，ShareGPT 1K 提示：SGLang ~16,200 tok/s vs vLLM ~12,500（约 29% 优势）。
- 前缀密集 RAG（相同系统 + 相同文档，不同问题）：SGLang 上最高 6.4 倍。
- 语音克隆工作负载：86.4% 前缀缓存命中率。
- SGLang 客户的生产命中率：50-99%，取决于提示纪律。
- 2026 年部署超过 400,000+ GPU。

### 顺序陷阱

6.4 倍的数字依赖于一致的提示模板顺序。如果你的客户端在某些请求中构造提示为 `[system, tools, context, history, question]`，在另一些中为 `[system, context, tools, history, question]`，树无法找到共享前缀。对人类来说看起来是共享前缀，对基数树来说是两个不同的序列。

工程师的杠杆：你的提示模板就是缓存键。固定顺序。将不可变内容（system、tools、schemas）放在最前面。检索上下文放在其次。用户问题放在最后。不要将动态内容交错插入前缀。

研究中的真实案例：将动态内容移出可缓存前缀，将一次部署从 7% 的缓存命中率提高到 74%。

### RadixAttention 的胜利与失败之处

胜利场景：
- RAG（相同检索前言，不同问题）。
- 代理（相同工具模式，不同查询）。
- 带有长系统提示的聊天。
- 带有重复前言的语音/视觉工作负载。

失败场景（回到 vLLM 水平吞吐量）：
- 具有独特提示的单发式生成（代码补全、无系统提示的开放式聊天）。
- 动态提示，每个请求将独特内容交错插入前缀。

### 为什么这是调度器问题，而不仅仅是内核问题

你可以将 KV 重用实现为一个内核技巧。SGLang 的洞察是：只有当调度器保持热分支驻留时重用才有回报。天真的"可用时重用"策略会在混合负载下导致缓存抖动。基数树索引的调度器是将内核技巧转化为 29% 生产优势的关键。

### 与 vLLM 的交互

这两个系统不是严格的竞争对手。在 2026 年，vLLM 添加了前缀缓存（`--enable-prefix-caching`）和缓存感知路由器（Rust 编写的 vLLM Router）。差距缩小但并未完全消失 — SGLang 的整个栈是基数优先的；vLLM 是嫁接上去的。对于以前缀重用主导的工作负载，SGLang 仍是默认选择。对于没有强前缀模式的通用推理，vLLM 保持同等或更好。

## 核心术语

| 术语 | 人们怎么说 | 实际含义 |
|------|-----------|---------|
| RadixAttention | "SGLang 那个东西" | KV 缓存作为基数树索引，共享前缀重用块 |
| 基数树 | "压缩字典树" | 每个节点拥有一个 token 范围及其 KV 块的树 |
| 缓存感知调度器 | "热分支优先" | 偏好共享驻留分支请求的调度器 |
| 前缀缓存命中率 | "你的提示有多少是免费的" | 从重用 KV 块服务的提示 token 占比 |
| FCFS | "先到先服务" | 破坏前缀局部性的默认调度 |
| 分支级别 LRU | "驱逐叶子" | 匹配基数形状的驱逐策略 |
| 提示模板顺序 | "缓存键" | 提示的组件顺序决定了树能共享什么 |
| 系统提示驻留 | "驻留前缀" | 保持不可变系统部分驻留以避免驱逐抖动 |
