# LLM 的影子流量、金丝雀部署和渐进发布

> LLM 发布结合了软件部署中最难的部分：没有单元测试、分散的失败模式、延迟的信号。顺序是（1）影子模式 — 将生产请求复制到候选模型，记录日志，比较，零用户影响；捕获明显的分布问题但不是质量保证；（2）金丝雀发布 — 渐进流量转移 10% → 25% → 50% → 75% → 100%，每步有门控；跟踪延迟百分位数、成本/请求、错误/拒绝率、输出长度分布、用户反馈率；（3）在稳定性确认后，对不同的替代方案进行 A/B 测试。非确定性是不可消除的 — 由于 GPU FP 非结合性加批次大小方差，在相同输入下的不同运行间准确率变化高达 15%。成本是变量，不是常量 — 一个好 20% 的模型可以每次调用贵 3 倍。回滚速度是决定性的：如果回滚需要重新部署，你就太慢了。策略存在于配置/标志中；模型存在于带固定摘要的仓库中；回滚 = 翻转策略 + 恢复阈值 + 固定旧模型，秒级完成。

**Type:** Learn
**Languages:** Python (stdlib, toy canary-progression simulator)
**Prerequisites:** Phase 17 · 13 (Observability), Phase 17 · 21 (A/B Testing)
**Time:** ~60 minutes

## 学习目标

- 区分影子模式（零影响比较）、金丝雀（实时流量渐进）和 A/B（稳定性确认的比较）。
- 列举五种 LLM 特定的金丝雀指标（延迟、成本/请求、错误/拒绝、输出长度分布、用户反馈）。
- 解释为什么 LLM 的非确定性（高达 15%）改变了发布中"稳定"的含义。
- 设计一个以秒计（策略翻转）而非小时计（重新部署）的回滚路径。

## 问题

你发布一个新模型。离线评估显示 3% 精度提升。你在生产中开启它。24 小时内，成本上升 40%，用户踩上升 8%，三个客户工单报告"奇怪的答案"。你回滚。重新部署需要 3 小时。你的周末被毁了。

每一点都是可避免的。影子模式会在任何用户看到之前捕获 40% 成本尖峰。金丝雀会在踩移动时在 10% 停下。策略标志回滚将花费 30 秒。纪律是填补"离线评估看起来不错"和"真实用户满意"之间差距的东西。

## 概念

### 影子模式

候选模型接收与生产相同的请求；输出被记录，不返回给用户。零用户影响。记录：

- 输出内容（与生产的差异）。
- Token 数量（成本差异）。
- 延迟。
- 拒绝和错误。

捕获：成本爆炸、长度退化、明显的拒绝变化、硬错误。不捕获：用户会感知的质量差异。影子是冒烟测试，不是质量测试。

### 金丝雀发布

带门控的渐进流量转移。典型进展：1% → 10% → 25% → 50% → 75% → 100%。每步在 5 项指标上门控：

1. **延迟百分位数** — P50、P95、P99。突破：金丝雀有 P99 > 基线的 1.5 倍。
2. **每请求成本** — 混合 $。突破：> 基线 20% 以上。
3. **错误 / 拒绝率** — 5xx 加显式拒绝。突破：基线的 2 倍。
4. **输出长度分布** — 均值 + P99。突破：分布偏移。
5. **用户反馈率** — 踩 / 工单提交。突破：基线的 1.5 倍。

### 非确定性是新的方差来源

相同输入产生非相同输出。原因：

- GPU FP 非结合性（浮点归约顺序因批次而异）。
- 批次大小方差（相同提示在 128 的批次 vs 16 的批次）。
- 采样（temperature > 0）。

测量结果：在相同评估集上运行间准确率变化高达 15%。发布中的"稳定"意味着指标在预期方差内，而非与基线相同。将门控设置得高于噪声地板。

### 成本是变量

一个好 20% 的模型可能每次调用贵 3 倍。成本/请求是五项门控之一。发布一个破坏单位经济学的"更好"模型是一个回滚案例。

### 回滚即武器

- 策略标志（功能标志系统）：在配置中翻转百分比；秒级完成。
- 模型固定（仓库摘要）：固定模型不会自动升级。
- 回滚 = 恢复标志 + 将固定摘要设为上一个。秒级，非小时级。

如果你的栈需要重新部署来回滚，在发布之前修复这个。

### 工具

**Argo Rollouts** / **Flagger** — Kubernetes 渐进交付控制器。与 Istio/Linkerd 加权路由集成。

**Istio 加权路由** — 服务网格级别的流量分割。

**KServe / Seldon Core** — 带内置金丝雀的模型推理。

**功能标志** — LaunchDarkly、Flagsmith、Unleash。策略级别翻转，无需重新部署。

### 指标节奏

金丝雀门控每 5-15 分钟检查一次，取决于流量量。1% 流量 10 req/min 下每个窗口给 50-150 个数据点 — 足够延迟但噪声大用于用户反馈。10% 下给约 10 倍。进展应在每个步骤暂停足够长的时间以积累足够的样本。

### A/B 步骤是可选的

如果新模型明显不同（不同行为、不同成本曲线、不同语调），在金丝雀通过后在 50% 处 A/B 测试它。如果只是改进版本，当金丝雀门控通过时跳到 100%。

### 你应该记住的数字

- 金丝雀进展：1% → 10% → 25% → 50% → 75% → 100%。
- 非确定性天花板：相同输入运行间方差高达 15%。
- 五项金丝雀指标：延迟、成本、错误/拒绝、输出长度、用户反馈。
- 成本门控：> 基线 20% 以上是突破。
- 回滚：秒级，非小时级。

## 练习

1. 运行 `code/main.py`。注入 25% 成本退化。金丝雀在哪个阶段停止？
2. 你的新模型离线精度提升 3% 但成本/请求 +18%。这是否发布？取决于策略 — 写出两条路径。
3. 设计一个端到端 60 秒内的回滚。列出所需基础设施。
4. 非确定性在你的评估上显示 ±7%。设置金丝雀门控以避免误报。你使用什么乘数？
5. 影子模式在金丝雀之前捕获到 40% 成本尖峰。编写在影子中触发的告警规则。

## 核心术语

| 术语 | 人们怎么说 | 实际含义 |
|------|-----------|---------|
| 影子模式 | "复制到新模型" | 零影响发送到候选模型用于记录 |
| 金丝雀 | "渐进流量" | 带门控的渐进用户暴露发布 |
| 门控 | "发布检查" | 阻止进展的指标阈值 |
| 非确定性 | "LLM 方差" | 不可消除的运行间差异 |
| 策略标志 | "标志翻转回滚" | 配置级别回滚，秒级非小时级 |
| 模型固定 | "仓库摘要" | 对模型版本的不可变引用 |
| Argo Rollouts | "K8s 渐进" | Kubernetes 原生金丝雀/回滚控制器 |
| KServe | "推理 K8s" | 带金丝雀原语的模型推理 |
| Istio 加权 | "网格分割" | 服务网格流量分割器 |
