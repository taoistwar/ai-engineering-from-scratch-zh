# 批处理 API — 50% 折扣作为行业标准

> 每个主要供应商都提供带有 50% 折扣和约 24 小时周转的异步批处理 API。OpenAI、Anthropic、Google 和大多数推理平台（Fireworks 批处理层、Together 批处理）实现相同的模式。将批处理与提示缓存叠加，过夜管线降至同步未缓存成本的约 10%。规则残酷而简单：如果不是交互式的，就属于批处理。内容生成管线、文档分类、数据提取、报告生成、批量标注、目录标记 — 任何容忍 24 小时延迟的东西，在迁移到批处理之前都是摆在桌上的金钱。2026 年的生产模式是将每个新的 LLM 工作负载分流到三个通道：交互式（带缓存的同步）、半交互式（带降级的异步队列）、批处理（过夜，叠加缓存输入）。伪装成交互式但容忍数分钟延迟的工作负载浪费最多。

**Type:** Learn
**Languages:** Python (stdlib, toy batch-vs-sync cost simulator)
**Prerequisites:** Phase 17 · 14 (Prompt & Semantic Caching)
**Time:** ~45 minutes

## 学习目标

- 说出三种供应商批处理 API（OpenAI、Anthropic、Google）和通用的 50% 折扣 + 24 小时周转保证。
- 在过夜分类工作负载上计算叠加批处理 + 缓存输入的成本，并与同步未缓存基线比较。
- 将工作负载分流为交互式/半交互式/批处理，并论证该通道。
- 说出两个陷阱：部分交互性（用户期望比 24 小时快）和输出模式漂移（批处理文件格式因供应商而异）。

## 问题

你的团队交付一个过夜报告生成管线。50,000 份文档，总结每份，聚类摘要，起草执行简报。同步运行需要 4 小时，成本 $2,000/晚。你听说了批处理 API。

批处理给你 50% 折扣。你还在系统提示上启用提示缓存（在所有 50k 调用中共享）。叠加后，账单降至 $180/晚 — 基线的约 9%。同样的管线，三次配置更改。

批处理是 LLM 成本工具包中最便宜但没人拉的杠杆。原因主要是组织上的：团队认为"实时"，而 SLA 实际上是"在早上之前"。本课是关于不把 90% 的账单留在桌上。

## 概念

### 三种批处理 API

**OpenAI Batch API**：带上请求列表的 JSONL 文件上传。承诺 24 小时周转（实践中通常约 2-8 小时）。输入和输出 token 50% 折扣。`/v1/batches` 端点。符合缓存条件的输入也获叠加的缓存输入定价。

**Anthropic Message Batches**：JSONL 上传。24 小时周转。50% 折扣。支持 `cache_control` — 缓存写入是显式的，读取在批处理内自动发生。

**Google Vertex AI Batch Prediction**：BigQuery 或 GCS 输入。Gemini 类似 50% 折扣。与 Vertex 管线集成。

### 语义：异步，不慢

批处理是"我承诺在 24 小时内返回" — 不是"这将需要 24 小时"。典型 P50 是 2-6 小时。供应商在你的 GPU 库存利用不足的峰谷窗口安排你的批处理。

### 与缓存叠加

具有相同 4K-token 系统提示的 5 万份文档总结：

- 同步未缓存：50000 × ($input × 4000 + $output × 200) 全额费率。
- 同步缓存：系统提示在首次写入后缓存；剩余 49999 获得 10 倍更便宜的输入。
- 批处理缓存：以上全部加上读取和写入 50% 折扣。

叠加：批处理 + 缓存 = 同步未缓存账单的约 10%。任何过夜运行并有共享系统提示的工作负载都应使用此方案。

### 工作负载分流

**交互式** — 用户等待响应。TTFT 重要。带提示缓存的同步调用。不能批处理。

**半交互式** — 用户提交任务，数分钟后回来查看。带降级到同步的异步队列，如果批处理不可用。思考中等批量的 RAG 索引。

**批处理** — 用户期望"在早上之前"或"下一小时内"获得结果。内容管线、规模化分类、离线分析。始终批处理，始终叠接缓存。

常见错误：因为管线在生产中就将一切都分类为交互式。生产不是延迟规范 — SLA 才是。

### 部分交互性陷阱

有些功能看起来是交互式的但容忍 5-10 分钟。示例：带有"刷新"按钮的过夜客户健康报告。用户点击刷新；等待 10 分钟没问题。团队将其作为同步交付。50 个并发刷新成本是批处理并通过邮件交付的 10 倍。

要问的问题："24 小时对用户意味着什么？"如果答案是"他们不会注意到"，就批处理它。

### 输出模式陷阱

批处理文件格式因供应商而异：

- OpenAI：JSONL，每行一个请求。
- Anthropic：JSONL，每行一条消息；嵌入响应格式。
- Vertex：BigQuery 表或 GCS 前缀带 TFRecord。

编写跨供应商的"一个批处理客户端"意味着每个供应商需要适配代码。宣传多供应商批处理的网关（Portkey、LiteLLM 某些层）仍然是对原始格式的薄包装。

### 你应该记住的数字

- 跨供应商批处理折扣：输入 + 输出统一 50%。
- 周转 SLA：保证 24 小时，典型 P50 2-6 小时。
- 叠加批处理 + 缓存输入：同步未缓存成本的约 10%。
- 工作负载分流规则：如果 24 小时延迟可接受，始终批处理。

## 核心术语

| 术语 | 人们怎么说 | 实际含义 |
|------|-----------|---------|
| Batch API | "异步折扣" | 24 小时周转 50% 折扣 |
| JSONL | "批处理格式" | 每行一个 JSON 请求；OpenAI/Anthropic 标准 |
| Message Batches | "Anthropic 批处理" | Anthropic 批处理 API 产品名称 |
| Batch prediction | "Vertex 批处理" | Vertex AI 批处理 API 产品 |
| 周转 SLA | "24 小时承诺" | 保证，非典型；典型是 2-6 小时 |
| 工作负载分流 | "交互性决策" | 交互式/半交互式/批处理路由决策 |
| 输出模式 | "响应格式" | 每供应商 JSONL 布局；不可移植 |
| 叠加折扣 | "批处理 + 缓存" | 两者都适用时约占未缓存同步账单的 10% |
