# LLM 的 FinOps — 单位经济学和多租户归因

> 传统 FinOps 在 LLM 支出上失效。成本是 token 交易，不是资源运行时间。标签不映射 — API 调用是交易，不是资产。工程决策（提示设计、上下文窗口、输出长度）是财务决策。2026 年的手册有第一天就需要仪器化的三个归因维度：按用户 (`user_id`) 用于座位定价和扩展，按任务 (`task_id` + `route`) 用于产品面的成本和优先级，按租户 (`tenant_id`) 用于单位经济学和续费。四个 token 层 — 提示、工具、记忆、响应 — 一个桶隐藏支出。多租户产品的执行阶梯：每租户速率限制（预期峰值的 2-3 倍，明确的 429 + retry-after）；每日支出上限（合同上限的 1.5-3 倍；触发速率收紧 + 告警）；支出 z-score > 4 时的终止开关（自动暂停 + 寻呼值班）。归因模式：标记聚合、遥测连接（追踪 ID → 计费；最高准确率）、采样外推、基于模型的分配、事件溯源、实时流式。单位指标：每解决的查询成本、每生成的制品成本 — 不是 $/M token。追溯标记总会遗漏；在请求创建时就仪器化。

**Type:** Learn
**Languages:** Python (stdlib, toy cost-attribution simulator with kill switch)
**Prerequisites:** Phase 17 · 13 (Observability), Phase 17 · 14 (Caching)
**Time:** ~60 minutes

## 学习目标

- 解释为什么传统 FinOps（标签 + 层级）在 LLM 支出上失效，并说出三个新的归因维度。
- 列举四个 token 层（提示、工具、记忆、响应）以及为什么单桶计费隐藏成本。
- 为多租户产品设计执行阶梯（速率 → 支出上限 → 终止开关）。
- 选择单位指标（每解决的查询/制品成本）而非 $/M token。

## 问题

你的账单是 $40,000。你不知道：
- 哪个租户花了这些钱。
- 哪个产品功能驱动了支出。
- 是否有单个用户是滥用性的。
- 是提示膨胀、工具调用还是记忆放大是罪魁祸首。

供应商侧的标记聚合对云资源有效（EC2、S3），标签传播到费用行项目。LLM API 调用不会自动标记 — 你必须在调用点标记 user/task/tenant 并贯穿始终。追溯归因总会遗漏边缘情况。

## 概念

### 三个归因维度

**按用户** (`user_id`)：谁花了什么。驱动座位定价、扩展对话、识别重度用户。

**按任务** (`task_id` + `route`)：哪个产品面花了多少。驱动功能优先级、干掉昂贵功能的决策。

**按租户** (`tenant_id`)：哪个客户是盈利的。驱动单位经济学、续费定价、层级阈值。

第一天就在调用点仪器化所有三个维度。追溯总是更糟。

### 四个 token 层

| 层 | 示例 | 占总量的典型百分比 |
|-------|---------|---------------------|
| 提示 | 系统 + 用户输入 | 40-60% |
| 工具 | 反馈回来的工具调用结果 | 20-40%（代理工作负载） |
| 记忆 | 先前的对话 / 检索到的文档 | 10-30% |
| 响应 | 模型输出 | 10-30% |

将四个全部放在一个桶中使优化盲目。在你的归因模式中将它们拆分。

### 执行阶梯

1. **速率限制**按租户。预期峰值的 2-3 倍。返回 429 带 `Retry-After`。租户感到摩擦；不会有意外的账单。

2. **每日支出上限**按租户。合同上限的 1.5-3 倍。触发：收紧速率限制 + 告警客户成功。

3. **终止开关**在支出 z-score > 4 相对于租户基线时。自动暂停租户；寻呼值班；升级到运维 + CS。

### 归因模式

- **标记聚合**：在元数据头打标记；稍后聚合。简单；粗糙。
- **遥测连接**：通过追踪 ID 将追踪与计费连接。最高准确率。成熟团队所做的。
- **采样 + 外推**：采样 5-10%，乘。对于粗略支出有成本效益；遗漏尾部。
- **基于模型的分配**：回归推断成本驱动因素。用于没有标签的传统数据。
- **事件溯源**：成本作为流中的事件（Kafka / Kinesis）。实时。
- **实时流式**：仪表板亚秒更新。

### 每 X 成本是单位指标

$/M token 是供应商术语。产品指标：

- 每解决的客服工单成本。
- 每生成的文章成本。
- 每次成功的代理任务成本。
- 每用户会话分钟成本。

将成本绑定到产品结果上。否则优化是无所锚定的。

### 成本归因追踪形状

```
trace_id: abc123
  user_id: u_42
  tenant_id: t_7
  task_id: task_classify_doc
  route: model_haiku
  layers:
    prompt_tokens: 1800
    tool_tokens: 600
    memory_tokens: 400
    response_tokens: 150
  cost_usd: 0.0135
  cached_input: true
  batch: false
```

在每次调用上发出。存储到数据湖中。按维度聚合。Phase 17 · 13 的可观测性栈是这所在的地方。

### 复合节省栈

栈：缓存 + 批处理 + 路由 + 网关。全部四个：
- 缓存 L2（Phase 17 · 14）：约 10 倍更便宜的输入。
- 批处理（Phase 17 · 15）：50% 折扣。
- 路由到廉价模型（Phase 17 · 16）：60% 成本降低。
- 网关效率（Phase 17 · 19）：冗余 + 重试。

最佳情况叠加：约为朴素基线的 5-10%。大多数团队投入了 2-3 个杠杆；很少叠加全部四个。

### 你应该记住的数字

- 归因维度：按用户、按任务、按租户。
- 四个 token 层：提示、工具、记忆、响应。
- 终止开关：支出 z-score > 4。
- 单位指标：每解决的查询成本，而非 $/M token。
- 叠加优化：可能为基线的约 5-10%。

## 核心术语

| 术语 | 人们怎么说 | 实际含义 |
|------|-----------|---------|
| 按用户归因 | "用户级成本" | 每次调用标记 `user_id` |
| 按任务归因 | "功能成本" | `task_id` + `route` 识别产品面 |
| 按租户归因 | "客户成本" | `tenant_id`；驱动单位经济学 |
| 四个 token 层 | "成本层" | 提示 + 工具 + 记忆 + 响应 |
| 速率限制 | "429 护栏" | 在网关执行的每租户上限 |
| 每日支出上限 | "每日天花板" | 带告警的租户范围预算 |
| 终止开关 | "自动暂停" | 支出 z-score > 4 触发自动暂停 |
| 每解决成本 | "产品单位指标" | 成本绑定到产品结果，而非 token |
| 遥测连接 | "追踪到计费" | 最高准确率归因模式 |
| 叠加优化 | "缓存+批处理+路由+网关" | 复合节省到基线的约 5-10% |
